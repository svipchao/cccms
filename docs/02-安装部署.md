# 安装部署

> 本文覆盖：环境要求 → 后端安装 → 数据库初始化 → 启动 → 前端安装 → Docker → 生产部署 → 升级。按顺序执行即可从零跑通。

---

## 一、环境要求

| 项 | 要求 | 说明 |
|----|------|------|
| PHP | >= 8.1（推荐 8.3） | 必须启用 `pdo`、`pdo_mysql`、`pcntl`；建议 `redis`、`event` |
| MySQL | >= 8.0 | InnoDB，字符集 `utf8mb4` / 排序规则 `utf8mb4_0900_ai_ci`；使用 JSON 列与 CHECK 约束 |
| Redis | >= 5.0 | 验证码、登录限流、配置缓存、会话分界线 |
| Node.js | >= 18 | 仅前端构建需要 |
| Composer | 2.x | 后端依赖 |

### 1.1 扩展说明

- **`pcntl`**：定时任务调度进程需要（仅 Linux / macOS 生效）。
- **`redis`**：装了 phpredis 扩展则使用扩展，否则自动回退纯 PHP 的 `predis/predis`（见 `server/config/redis.php`）。
- **`event`**：可选，提升 Webman 事件循环性能。

> ⚠️ **注意**：Windows 下 Webman 无法运行自定义进程（`pcntl` 不可用），因此**定时任务调度进程在 Windows 不生效**。开发环境如需要，请在 Linux / WSL / Docker 中运行。

## 二、后端安装

### 2.1 安装依赖

```bash
cd server
composer install
```

### 2.2 创建数据库并导入

自行创建数据库（字符集 `utf8mb4`），然后导入两份脚本：

```bash
# 1) 建库
mysql -uroot -p -e "CREATE DATABASE cccms DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_0900_ai_ci;"

# 2) 表结构（27 张表，清单见 docs/13-数据模型.md）
mysql -uroot -p cccms < plugin/cccms/db/schema.sql

# 3) 初始化种子（超管角色、admin 账号、受控表登记、系统配置默认值）
mysql -uroot -p cccms < plugin/cccms/db/seed.sql
```

`seed.sql` 全部使用 `INSERT IGNORE`，**可重复执行**，升级时直接再跑一遍不会破坏已有数据。

### 2.3 配置环境变量

复制示例文件并按环境修改（`.env` 已被 `.gitignore` 忽略，不会提交）：

```bash
cd server
cp .env.example .env
```

**本地开发务必设置 `APP_DEBUG=true`**，否则未预期的异常只会返回「服务器内部错误」。

| 环境变量 | 默认值 | 说明 |
|----------|--------|------|
| `APP_DEBUG` | `false` | 异常详情开关。**默认关闭（安全默认）**；生产必须保持 `false` |
| `DB_HOST` | `127.0.0.1` | 数据库地址 |
| `DB_PORT` | `3306` | 端口 |
| `DB_DATABASE` | `cccms` | 库名 |
| `DB_USERNAME` | `root` | 用户名 |
| `DB_PASSWORD` | `123456` | 密码 |
| `DB_DEBUG` | `false` | 是否输出 SQL 调试信息 |
| `REDIS_HOST` | `127.0.0.1` | Redis 地址 |
| `REDIS_PORT` | `6379` | 端口 |
| `REDIS_PASSWORD` | 空 | 密码 |
| `REDIS_DB` | `0` | 库号 |
| `JWT_SECRET` | 内置开发密钥 | **生产务必替换**；HS256 要求 >= 32 字节 |
| `DATA_ENCRYPT_KEY` | 内置开发密钥 | 字段级 `encrypt` 的 AES-256-GCM 种子；**一旦更换，历史加密字段无法解密（不做密钥轮换）** |
| `STORAGE_DRIVER` | `local` | `local` / `oss` / `cos` / `qiniu`；**仅作建库前的初始值**，之后以「配置管理 → 上传」的 `upload.storage_driver` 为准 |
| `LOG_ARCHIVE_DAYS` / `LOG_ARCHIVE_BATCH` / `LOG_ARCHIVE_DRIVER` / `LOG_ARCHIVE_PATH` | `30` / `1000` / 空 / `log-archive` | 日志归档参数（可选）；`DRIVER` 留空则跟随当前存储驱动 |
| `CCCMS_UPGRADE_SOURCE` / `CCCMS_UPGRADE_URL_GITEE` / `CCCMS_UPGRADE_URL_GITHUB` | `gitee` / 官方地址 | 上游同步源（可选，见 §6.1）。公开仓库可匿名拉取；私有仓库在 URL 里带令牌即可 |

> 云存储凭证（`OSS_*` / `COS_*` / `QINIU_*`）**不在 `.env` 配置**，统一在后台
> 「系统设置 → 配置管理 → 上传」填写：选中哪个驱动，页面就只显示该驱动的
> AccessKey / Secret / Bucket / Endpoint(Region) / 域名等字段，密钥类项以密文存库。

生成随机密钥：

```bash
php -r "echo bin2hex(random_bytes(32)), PHP_EOL;"
```

> 完整清单见 `server/.env.example`。**推荐用 `.env` 或部署平台注入，不要写进代码。**

### 2.4 同步菜单与权限节点

```bash
cd server

php webman cccms:menu-sync      # 同步 db/menu.php 的目录 / 菜单（type=1/2）
php webman cccms:perm-scan      # 扫描控制器注解，生成按钮节点（type=3）
php webman cccms:db-upgrade     # 已有库补新增表 / 列 / 索引（全新装的环境可跳过，幂等可重复执行）
```

> 菜单（目录 / 菜单）由 `db/menu.php` 声明，按钮节点由控制器注解生成，二者都写入 `sys_menu`，是权限体系的数据来源。

### 2.5 启动

```bash
# Linux / macOS
php start.php start -d     # 后台守护（调试用前台：php start.php start）

# Windows（无自定义进程，定时任务不生效）
php windows.php
```

默认监听 `http://0.0.0.0:8787`（见 `server/config/process.php`）。停止 / 重载 / 状态查看见 [11-常用命令与运维 §三](11-常用命令与运维.md#三启动--停止--重载)。

快速自检：

```bash
curl http://127.0.0.1:8787/ping
# {"code":0,"message":"ok","data":{"pong":true,"time":...}}
```

### 2.6 默认账号

| 账号 | 密码 | 说明 |
|------|------|------|
| `admin` | `admin123` | 内置超管，**首次登录后请立即修改密码** |

## 三、前端安装

```bash
cd frontend
npm install
npm run dev        # http://localhost:5173
npm run build      # 产物在 dist/
npm run preview    # 本地预览构建产物
```

### 3.1 接口代理

开发期前端统一以 `/api` 前缀调用接口，由 Vite 代理到后端（`frontend/vite.config.ts`）：

```
/api/xxx      →  http://127.0.0.1:8787/xxx   （转发时去掉 /api）
/storage/xxx  →  http://127.0.0.1:8787/storage/xxx  （附件缩略图与「查看」新窗口）
```

接口基地址通过环境变量 `VITE_API_BASE`（默认 `/api`）配置，见 `frontend/.env.development` / `.env.production`。

> `/storage` 也必须代理：附件 URL 是相对路径（`/storage/...`），`<img>` 缩略图与「查看」
> 的 `window.open` 都从 5173 发请求，若不代理，Vite 会把 `/storage` 当 SPA 路由回退到
> `index.html`，于是「查看」跳到 `#/dashboard`。生产环境则由 Nginx 反代 / 托管（见 §5.2 / §5.3）。

### 3.2 生产环境部署前端

```bash
npm run build
# 将 dist/ 交给 Nginx 托管，并把 /api 反向代理到后端 8787
```

> ⚠️ **注意**：前端使用 **hash 路由**（`createWebHashHistory`），Nginx 不需要额外的 `try_files` 兜底；访问形如 `https://your.domain/#/cccms/user`。

## 四、Docker 部署

`server/` 下提供了 `Dockerfile` 与 `docker-compose.yml`，**一键启动 Webman + MySQL + Redis**。

### 4.1 准备变量

compose 与 Webman **共用同一份 `server/.env`**：

```bash
cd server
cp .env.example .env
# 至少设置：JWT_SECRET、DATA_ENCRYPT_KEY、DB_PASSWORD
```

> `docker-compose.yml` 里 `JWT_SECRET` / `DATA_ENCRYPT_KEY` 使用 `${VAR:?请在 server/.env 中设置}`
> 语法：**未设置会直接报错退出**，避免用内置开发密钥上生产。

### 4.2 启动

```bash
cd server
docker compose up -d --build
```

| 项 | 说明 |
|----|------|
| webman | 基于 `php:8.3-cli-alpine`；启用 `pdo_mysql` / `pcntl` / `opcache`（redis 扩展可选，见构建参数） |
| 构建方式 | **多阶段**：`builder` 层装编译工具链、编译扩展、`composer install`，`runtime` 层只拷回 PHP 配置 / 扩展 / `vendor` / 源码，编译工具链不进最终镜像 |
| 镜像内容 | **代码与依赖打进镜像**（依赖层单独缓存，`composer install --no-dev --optimize-autoloader`），不再依赖 volume 挂载源码 |
| 健康检查 | webman 服务在 Dockerfile 与 compose 中**各声明一次**（同一口径）：容器内 `wget http://127.0.0.1:8787/healthz`（就绪探针，依赖故障返回 503 → unhealthy），`docker compose ps` 会显示 `healthy`。`/healthz` 走 IP 白名单，容器内来源是回环地址，默认就在白名单里 |
| mysql | `mysql:8.0`，首次初始化时**自动导入** `db/schema.sql` 与 `db/seed.sql` |
| redis | `redis:7-alpine`，开启 AOF 持久化 |
| 持久化 | 命名卷：`runtime` / `storage` / `mysql-data` / `redis-data` |

启动后确认三个服务都健康：

```bash
docker compose ps            # webman / mysql / redis 的 STATUS 都应为 Up (healthy)
```

### 4.3 首次初始化

```bash
docker compose exec webman php webman cccms:menu-sync
docker compose exec webman php webman cccms:perm-scan
```

访问 `http://localhost:8787`，默认账号 `admin / admin123`。

> 构建参数 `INSTALL_REDIS_EXT=0` 可跳过 pecl 安装 redis 扩展（改用纯 PHP 的 predis）。
> 只想本地试用而不装 redis 扩展时可用：`docker compose build --build-arg INSTALL_REDIS_EXT=0`。

## 五、生产部署清单

### 5.1 后端

1. **确认 debug 关闭**：`debug` 读取 `APP_DEBUG`，**默认即 `false`**；请勿在生产设成 `true`。
2. **替换密钥**：注入 `JWT_SECRET` 与 `DATA_ENCRYPT_KEY`（随机、足够长）。
3. **数据库账号**：使用最小权限账号，不要用 `root`。
4. **进程守护**：推荐 supervisor 或 systemd 管理 `php start.php start`，并配置自动重启。
5. **目录权限**：`server/runtime` 需可写；`server/public/storage` 需可写。
6. **Web 服务器**：Nginx 反向代理到 `127.0.0.1:8787`；`/storage/*` **必须反代到后端**（附件的公开 / 私有开关由后端判定，Nginx 直接托管会绕过，见 §5.2）。

### 5.2 `public/storage` 安全（硬要求）

两条都要满足：

1. **禁止在上传目录解析 PHP**，否则同域上传目录可执行脚本 = 任意代码执行；
2. **`/storage/*` 必须由后端反代**，不要用 Nginx `root` 直接托管。附件的「公开 / 私有」判定、
   `nosniff`、非图片 / PDF 强制下载都在 `StorageGuard` 中间件里 —— **只有请求经过后端才会执行**。
   直接托管等于把开关整体作废（所有附件回到「拿到 URL 就能下载」）。

直接用仓库样例（`/api` 与 `/storage` 都反代）：

```bash
cp deploy/nginx.conf.example /etc/nginx/conf.d/cccms.conf
```

内容见 [deploy/nginx.conf.example](../deploy/nginx.conf.example)（改 `root` 与端口即可）。

若只能由 Nginx 直接托管，至少禁止解析脚本，并**明确接受「公开 / 私有开关失效」**：

```nginx
location ^~ /storage/ {
    location ~ \.(php|php5|phtml|phar)$ { deny all; }
}
```

> **建议**：把附件切到独立域名 / CDN（`upload.url_prefix` 或云存储驱动），从根上隔离上传目录与主站；
> 切到云存储后访问控制由云侧负责（私有 bucket + 签名 URL），本地的 `is_public` 不再参与。

### 5.3 前端

```nginx
server {
    listen 80;
    server_name your.domain;
    root /var/www/cccms/frontend/dist;
    index index.html;

    location /api/ {
        proxy_pass http://127.0.0.1:8787/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    # 附件（本地存储）**必须**反代到后端：
    #   1. 相对路径 /storage/... 才能命中，否则会被下面的 `location /` 回退到 index.html
    #      （「查看」会跳到 #/dashboard）；
    #   2. 公开 / 私有开关与响应头加固都在后端 StorageGuard 里，Nginx 直接托管会全部绕过。
    # 若附件切了独立域名 / CDN（upload.url_prefix），则不需要这一条。
    location ^~ /storage/ {
        proxy_pass http://127.0.0.1:8787;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location / { try_files $uri $uri/ /index.html; }
}
```

> `/storage` 的安全要求（禁止在上传目录执行 PHP、附件公开 / 私有开关、防 SVG/HTML 存储型 XSS）
> 见 §5.2。反代是这些措施生效的前提：开关判定与响应头加固都由后端 `StorageGuard` 中间件完成。

### 5.4 反向代理下的真实 IP 溯源（必配）

后台多处依赖「客户端真实 IP」：登录失败锁定（`security.login_fail_limit` /
`security.login_fail_ip_limit`）、登录日志、操作日志、在线用户。

**为什么不能靠 `X-Forwarded-For` 直接取**：该头是客户端可以自己带的。若应用无条件信任它，
攻击者每次换一个伪造 IP，就能让 **IP 维度**的防撞库限流失效，并把假 IP 写进审计日志。
所以本系统只在**直连来源命中可信代理白名单**时才解析转发头，且采用「**取最右非可信 IP**」
算法（从 XFF 最右端向左跳过所有可信代理，遇到的第一个非可信地址才是真实客户端）。

**配置**：「系统设置 → 配置管理 → 安全 → 可信代理」（`security.trusted_proxies`），
填**反向代理 / 网关的地址**（IP 或 CIDR，逗号或换行分隔），例如：

| 部署形态 | 建议填写 |
|---|---|
| 宿主机 Nginx → `127.0.0.1:8787` | `127.0.0.1` |
| Nginx 与应用同一 Docker 网络 | 该网络的网段，如 `172.18.0.0/16` |
| 多级代理（CDN + Nginx） | 逐层列出，如 `172.18.0.0/16, 10.0.0.0/8` |

> ⚠️ **留空的含义**：留空 = **不采信任何转发头**，直接用 TCP 直连 IP。
> 这是安全默认值 —— 反代部署下所有请求都会归到网关 IP（IP 维度限流会互相误伤、
> 日志也看不到真实来源），因此**生产环境必须显式配置**。
>
> ⚠️ **不要**把 `0.0.0.0/0` 填进去，那等于恢复成「完全信任 XFF」。

代理侧必须**覆写**而不是透传该头（Nginx 用 `$proxy_add_x_forwarded_for`）：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8787/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    # $proxy_add_x_forwarded_for = 客户端带来的 XFF + $remote_addr（由本机追加）
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

**验证是否生效**：

```bash
# 1) 从「操作日志」页看一条自己刚产生的写操作，IP 应是你本机出口 IP，而不是网关 IP
# 2) 伪造探针：带一个假 XFF 打登录接口，日志里的 IP 不应变成 1.2.3.4
curl -s -X POST 'https://your.domain/api/auth/login' \
  -H 'Content-Type: application/json' \
  -H 'X-Forwarded-For: 1.2.3.4' \
  -d '{"username":"admin","password":"wrong"}'
```

### 5.5 首次上线后

1. 用 `admin / admin123` 登录并**立即改密**。
2. 「系统设置 → 配置管理」按需调整品牌、界面、安全、上传、日志配置。
3. 按需在「权限配置 → 数据权限 → 受控表」登记业务表。
4. 检查定时任务：`seed.sql` 已预置「清理历史日志」（`LogCleanTask`，每天 03:00）。
5. **（可选）日志归档到对象存储**：`seed.sql` 另预置「日志归档到对象存储」
   （`LogArchiveTask`，每天 04:00，**默认停用**）。需要长期留存操作日志时，先按
   `config/log.php` 的 `archive` 段（或环境变量 `LOG_ARCHIVE_DAYS` / `LOG_ARCHIVE_BATCH` /
   `LOG_ARCHIVE_DRIVER` / `LOG_ARCHIVE_PATH`）确认天数与目标存储，再在「定时任务」里启用；
   也可手动执行 `php webman cccms:log-archive --dry-run` 先看会归档多少条。
   详见 [11-常用命令与运维 §1.11](11-常用命令与运维.md#111-cccmslog-archive--归档历史日志到对象存储)。

### 5.6 接入找回密码真实网关（P2-3，上线前必配）

未配置真实网关时，找回密码链路**降级为日志输出**（开发环境可走通流程，但不会真发邮件 / 短信）。上线前按实际渠道在「系统设置 → 配置管理」补齐并**实测送达**：

| 分组 | 配置项 | 说明 |
|------|--------|------|
| 安全 | `security.reset_channel` | 找回密码渠道：`off` / `email` / `sms` / `both`（默认 `off`） |
| 邮箱 | `mail.enabled` | 置 `1` 启用；随后 `mail.host` / `port` / `username` / `password` / `encryption`（`tls` / `ssl`）/ `from_address` / `from_name` |
| 短信 | `sms.enabled` | 置 `1` 启用；`sms.driver` 选实际服务商，`gateway_url` / `method` / `params` / `headers` / `sign_name` 按服务商文档填写 |

> 验证码频率控制已内置（`security.reset_send_interval` / `security.reset_max_attempts` / `security.reset_daily_limit` / `security.reset_code_ttl`），网关打通后无需额外配置；但 IP 维度限流依赖 `security.trusted_proxies` 正确配置（见 §5.4）。

> ⚠️ 邮件 / 短信网关密钥走 `password` 类型配置项，加密存储（`sys_config` + `Cipher`）。本项属**部署配置动作**，代码侧无改动 —— 完成后从 [开发计划](开发计划.md) 移除该条。

## 六、升级

### 6.1 从上游同步框架代码

若本项目衍生自开源 CCCMS 仓库（业务写在 `plugin/*` 里），框架自身的更新可直接拉取——
命令会先做「基线 / 本地 / 上游」三方比对，**只覆盖本地没改过的文件**，其余只报告：

```bash
cd server
php webman cccms:update --init     # 首次：登记基线，并列出本地相对上游改过哪些文件
php webman cccms:update --check    # 预览：上游改了什么、能否安全覆盖（不写文件）
php webman cccms:update            # 同步：自动覆盖安全项，冲突项只报告
php webman cccms:update --force    # 冲突项也覆盖（覆盖前自动备份到 runtime/）
```

上游配了国内（Gitee）与国外（GitHub）两个镜像，可用 `--source=gitee|github` 切换（**默认 `gitee`**）；
公开仓库可直接匿名拉取，**不需要任何凭据**。也可以直接在后台「**系统设置 → 自动升级**」里操作：
切换镜像、选择目标版本、查看变更文件与行数、提交记录，再一键升级。

> **该功能仅限本地开发环境**：总开关默认关闭，且要求仓库根存在 `frontend/package.json`；
> 线上是「已构建」形态（前端产物在 `public` 下、目录结构与仓库不一致），会被自动拦住 —— 线上请走发布流程。
> 私有仓库需在 URL 里带令牌（`CCCMS_UPGRADE_URL_GITEE=https://<账号>:<令牌>@gitee.com/<owner>/<repo>.git`）；
> 排查同步失败见 [11-常用命令与运维 §1.10](11-常用命令与运维.md#110-cccmsupdate--从上游仓库同步框架更新)。

配置见 `plugin/cccms/config/upgrade.php`（同步源 / 跟踪分支 / 排除路径 / 备份位置）。
分类口径与回滚方式见 [11-常用命令与运维 §1.10](11-常用命令与运维.md#110-cccmsupdate--从上游仓库同步框架更新)。

### 6.2 升级后的例行命令

代码更新后：

```bash
cd server
composer install                 # 依赖有变时
php webman cccms:db-upgrade      # 幂等补表/列/索引，并执行各业务插件的 schema
php webman cccms:menu-sync       # 同步菜单声明变化
php webman cccms:perm-scan       # 同步按钮节点变化
composer test                    # 回归纯逻辑用例（可选）
php start.php reload             # 平滑重载

cd ../frontend && npm install && npm run build
```

> `composer test` 中需要数据库的用例在库不可用时**自动跳过**，因此可以在任意环境安全执行。

> 后台侧边栏用户卡片的「系统刷新」下拉（范围：`all` / `menu` / `perm` / `cache`）提供与 CLI **共用同一份实现**的图形入口，适合日常小改动后刷新。

## 七、安装常见问题

| 现象 | 原因 / 处理 |
|------|-------------|
| 启动报 `Class "Redis" not found` | 未装 phpredis 扩展且未安装 predis 依赖；`composer install` 会装 `predis/predis`，或安装 phpredis 扩展 |
| 报「接口未声明权限」500 | 新增控制器方法没写权限注解（fail-closed 生效），补 `#[Permission]` / `#[NoAuth]`，见 [05-鉴权与权限](05-鉴权与权限.md) |
| 菜单 / 按钮看不到 | 未执行 `menu-sync` / `perm-scan`，或当前角色未授权该节点 |
| 列表接口报「列不存在」 | 模型参与数据权限但表中没有对应归属列，需要在模型里声明语义或 `$dataScope = false`，见 [06-数据权限](06-数据权限.md) |
| 定时任务不执行 | Windows 不支持自定义进程；Linux 确认 `php start.php status` 中 `crontab` 进程在运行 |

更多排错见 [12-常见问题与排错](12-常见问题与排错.md)。
