# 常用命令与运维

> 日常开发、发布、排障会用到的命令与配置。机制说明见 04 / 14~18。

---

## 一、后端命令

```bash
cd backend

uv sync                                    # 安装依赖
uv run python -m cccms.cli init-db         # 按元数据建表
uv run python -m cccms.cli seed            # 初始化租户/角色/管理员/菜单/内置任务
uv run python -m cccms.cli check           # 路由权限声明校验
uv run python -m cccms.cli audit-verify    # 校验审计哈希链（异常时退出码非 0）

uv run uvicorn cccms.main:app --reload --port 8000
uv run python -m cccms.scheduler            # 定时任务进程（独立）
uv run python -m cccms.dev                  # 本地同时起 API + 调度器

uv run ruff check src
uv run ruff format src
uv run mypy src
uv run pytest
```

| 命令 | 适用场景 | 注意 |
|------|----------|------|
| `init-db` | 全新数据库 | 已存在的表不会被修改 |
| `seed` | 首次初始化或同步菜单节点 | 可重复执行 |
| `check` | 提交前、发布前 | 漏写权限声明会失败 |
| `audit-verify` | 合规检查、故障排查 | 从链头开始校验，异常返回非 0 |
| `scheduler` | 生产常驻 | 只运行一个实例即可，锁在 Redis |

> **提示**：`seed` 会按 `api/` 中的 `@permission` 自动补齐按钮节点；新增接口后执行一次即可在角色授权里看到。

## 三、Redis 键

| 键 | 类型 | 用途 | TTL |
|----|------|------|-----|
| `cccms:token:bl:<jti>` | string | 单令牌黑名单 | 到令牌过期 |
| `cccms:token:cut:<user_id>` | string | 用户令牌签发水位 | 长期 |
| `cccms:online:s:<jti>` | hash | 在线会话详情 | 到令牌过期 |
| `cccms:online:index` | zset | 在线会话索引 | 随会话清理 |
| `cccms:captcha:<id>` | string | 图形验证码 | 短 |
| `cccms:login_fail:user:<name>` | string | 登录失败计数 | 窗口期 |
| `cccms:login_fail:ip:<ip>` | string | IP 失败计数 | 窗口期 |
| `cccms:rl:<user>:<path>` | string | 接口限流计数 | 窗口期 |
| `cccms:config:all:<tenant>` | string | 配置缓存 | 有 TTL，保存后主动清理 |
| `cccms:tenant:domain:<host>` | string | 域名→租户缓存 | 有 TTL |
| `cccms:dict:d:<ver>:<type>` | string | 字典数据缓存 | 版本号失效 |
| `cccms:auth:ctx:<ver>:<user>` | string | 权限上下文缓存 | 版本号失效 |
| `cccms:auth:ver` / `cccms:config:ver` / `cccms:dict:ver` | string | 版本号，递增即全量失效 | 长期 |
| `cccms:scheduler:lock` | string | 调度器选主 | 短 |
| `cccms:upload:<id>` | hash | 分片上传会话 | 有 TTL |

> ⚠️ **注意**：不要用 `FLUSHDB` 清理业务缓存，会同时清掉在线会话与令牌黑名单。优先删具体键或递增版本号。

## 四、关键配置

| 变量 | 默认 | 说明 |
|------|------|------|
| `CCCMS_ENV` | `dev` | `dev` / `test` / `prod` |
| `CCCMS_DEBUG` | `false` | 调试模式 |
| `CCCMS_DB_*` | 本机 | 连接与连接池 |
| `CCCMS_REDIS_URL` | 本机 | Redis |
| `CCCMS_JWT_SECRET` | 空 | 生产必填，≥32 字节 |
| `CCCMS_DATA_ENCRYPT_KEY` | 空 | 敏感配置加密 |
| `CCCMS_AUDIT_SIGNING_KEY` | 空 | 审计链签名 |
| `CCCMS_COOKIE_SECURE` | `false` | 生产必须 `true` |

| `CCCMS_STORAGE_LOCAL_ROOT` | `shared/uploads` | 附件目录 |

| `CCCMS_UPLOAD_MAX_MB` | `10` | 普通上传上限 |

| `CCCMS_SCHEDULER_POLL_INTERVAL` | `10` | 调度扫描间隔 |
| `CCCMS_CRON_LOCK_TTL` | `3600` | 任务锁兜底 TTL |
| `CCCMS_HEALTH_DISK_MIN_PERCENT` | `5` | 磁盘告警阈值 |
| `CCCMS_METRICS_ALLOW_IPS` | 本机 | 指标白名单 |
| `CCCMS_TRUSTED_PROXIES` | 空 | 可信代理，用于还原真实 IP |
| `CCCMS_UPGRADE_ENABLE` | `false` | 在线升级开关 |

完整列表见 `backend/.env.example` 与 `backend/src/cccms/config.py`。

## 五、探针与指标

| 端点 | 说明 |
|------|------|
| `GET /ping` | 进程存活，不查依赖 |
| `GET /healthz` | 数据库、Redis、磁盘；任一异常返回 503 |
| `GET /metrics` | Prometheus 文本格式，默认仅 `127.0.0.1` / `::1` |

指标：

| 指标 | 类型 | 用途 |
|---|---|---|
| `cccms_http_requests_total{method,route,status}` | Counter | RED 中的请求量与错误率（`route` 是路由模板，不含具体 ID） |
| `cccms_http_request_duration_seconds{method,route}` | Histogram | P95/P99 延迟 |
| `cccms_http_requests_in_flight` | Gauge | 并发在途请求 |
| `cccms_online_sessions` / `cccms_online_users` | Gauge | 在线会话与去重用户数 |
| `cccms_scheduler_heartbeat_age_seconds` | Gauge | 调度器心跳年龄，`-1` 表示从未上报 |
| `cccms_db_pool_checked_out` | Gauge | 连接池已借出连接数，逼近上限说明存在慢查询或长事务 |

> `route` 标签使用路由模板（如 `/api/user/{user_id}`），避免路径参数把时间序列基数打爆；未匹配路由记为 `unmatched`。

> **提示**：`/metrics` 的 IP 白名单是**请求来源 IP**。放在 Nginx 后面时，需配置 `CCCMS_TRUSTED_PROXIES` 才能拿到真实 IP；否则所有请求都像来自代理。

## 六、备份与恢复

### 6.1 备份

```bash
mysqldump --single-transaction --routines --triggers cccms > cccms-$(date +%F).sql
tar -czf shared-$(date +%F).tar.gz shared/
```

需要同时备份：

- MySQL：业务数据、配置、日志。
- `shared/uploads`：附件。
- `shared/exports`：可重新生成，但保留可减少重复导出。
- `backend/.env`：密钥与连接串（单独加密保管）。

### 6.2 恢复

1. 停止 `cccms-api` 与 `cccms-scheduler`。
2. 恢复数据库。
3. 恢复 `shared/`。
4. 确认 `.env` 密钥与备份时一致（否则加密配置无法解密）。
5. 启动并访问 `/healthz`。

> ⚠️ **注意**：`CCCMS_DATA_ENCRYPT_KEY` 丢失会导致 `secret` 类型配置与加密字段无法解密；换密钥前必须先解密再重新加密。

## 七、缓存与配置刷新

- 修改系统配置后自动清理当前租户缓存。
- 手工刷新：`POST /api/system/refresh`（权限 `cccms:config:refresh`）。
- 字典/权限变更：版本号递增，下一次读取自动回源。

排障顺序：

1. 确认数据库已更新。
2. 确认 Redis 中 `cccms:config:all:<tenant>` 已删除。
3. 仍不生效时检查是否连到了另一个 Redis 库。

## 八、日志

| 日志 | 位置/去向 |
|------|-----------|
| 应用日志 | stdout / systemd journal |
| 操作日志 | `sys_log` 表，后台可查 |
| 慢请求 | 应用日志 warning |
| 定时任务 | `sys_crontab_log` 表 |
| 审计链 | `sys_audit_seal` 表 |

清理策略：

- 内置任务「清理过期操作日志」默认每天 03:30 执行。
- 只清理早于 `CCCMS_LOG_KEEP_DAYS` 的日志。
- 租户级任务只清理本租户；平台租户可执行全量清理。
- 已封存日志受哈希链保护，后台删除接口会拒绝。
- 平台租户另有「清理过期导出文件」（每天 04:00）与「清理未完成分片」（每天 04:15，默认 48 小时）。

## 九、发布检查

```bash
# 后端
uv run python -m cccms.cli check
uv run ruff check src
uv run mypy src
uv run pytest

# 前端
cd ../frontend
npm run lint
npm run build
```

发布顺序：

1. 备份数据库与 `shared/`。
2. 构建前端并上传 `dist`。
3. 更新后端代码与依赖。
4. 如有模型变更，先在预发执行并验证 DDL。
5. 重启 API 与调度器。
6. 验证 `/healthz`、登录、权限、上传、导出。

## 十、安全加固清单

- [ ] 全站 HTTPS，`CCCMS_COOKIE_SECURE=true`
- [ ] 四项密钥随机生成且不入库
- [ ] 数据库/Redis 不对公网开放
- [ ] `/metrics`、`/docs`、`/openapi.json` 不暴露
- [ ] `shared/exports` 未配置为静态目录
- [ ] 初始管理员密码已修改
- [ ] 超管账号数量受控，开启登录失败告警
- [ ] 定期检查 `sys_log` 中的异常登录与高危操作
- [ ] 备份文件加密存放，恢复演练至少每季度一次
