# 常见问题与排错

> 按「现象」检索的 FAQ。每条给出：原因 → 定位方法 → 处理。排错时先看 `server/runtime/logs/` 与 `sys_log` 表。

---

## 一、安装与启动

### 1.1 启动报 `Class "Redis" not found`

- **原因**：`server/config/redis.php` 会在装了 `redis` 扩展时用 phpredis，否则用 `predis/predis`；若两者都没有就会报这个错。
- **处理**：优先安装 phpredis 扩展；或确认已执行 `composer install`（会装上 `predis/predis`）。

### 1.2 数据库连接失败 / 认证失败

- 检查 `server/plugin/cccms/config/database.php` 或环境变量 `DB_HOST` / `DB_DATABASE` / `DB_USERNAME` / `DB_PASSWORD` / `DB_PORT`。
- 确认已导入 `schema.sql` 与 `seed.sql`。

### 1.3 前端页面正常但接口全 404

- 确认后端已启动且监听 `8787`：`curl http://127.0.0.1:8787/ping`。
- 检查 Vite 代理：前端以 `/api` 前缀调用，代理到 `http://127.0.0.1:8787` 并**去掉 `/api`**。
- 查看 `server/runtime/logs/route-404.log`，里面有真实的方法与路径，可确认是否是路径拼错或后端未注册路由。
- 新增的接口未在 `config/route.php` 注册也会 404（默认路由已禁用）。

### 1.4 Windows 下定时任务不执行

- **原因**：Webman 的自定义进程依赖 `pcntl`，Windows 不支持。
- **处理**：在 Linux / WSL / Docker 中运行后端；或用系统计划任务定时调用接口。

### 1.5 端口 8787 被占用

- 改 `server/config/process.php` 的 `listen`，或释放端口。

### 1.6 Docker 启动报「请在 server/.env 中设置 JWT_SECRET」

- `docker-compose.yml` 对 `JWT_SECRET` / `DATA_ENCRYPT_KEY` 用了 `${VAR:?…}` 语法，
  **未设置会直接报错退出**（避免用内置开发密钥上生产）。
- 处理：`cd server && cp .env.example .env`，填好这两个变量后再 `docker compose up -d --build`。

### 1.7 本地开发看不到异常详情

- `debug` 由 `APP_DEBUG` 控制且**默认关闭**（安全默认）。在 `server/.env` 里设置
  `APP_DEBUG=true` 并重载进程即可。`ApiException` 的业务提示不受该开关影响，始终会返回。

### 1.8 本地没有 redis 扩展能用吗

- 可以。`server/config/redis.php` 会在装了 `redis` 扩展时用 phpredis，否则回退纯 PHP 的
  `predis/predis`（`composer install` 已包含）。Docker 构建可用
  `--build-arg INSTALL_REDIS_EXT=0` 跳过 pecl 安装。

### 1.9 命令行输出 `Qiniu\Config::__construct(): Implicitly marking parameter $z as nullable is deprecated`

- **原因**：`qiniu/php-sdk` 7.14.0（当前最新，上游尚未适配 PHP 8.4）源码里写的是
  `Region $z = null` 这类**隐式可空**参数，PHP 8.4 在**类编译**时抛 `E_DEPRECATED`。
  SDK 的 composer `files`（`src/Qiniu/functions.php` 首行引用 `Config::SDK_VER`）把它提前到
  每个进程启动，于是每条 CLI 命令、每个 worker 都刷一行，还会把命令自己的输出顶到下面。
- **更严重的同源问题**：webman 的错误处理器会把「`error_reporting` 覆盖到的错误」转成
  `ErrorException`，所以 PHP 8.4 下真正使用七牛驱动时（`UploadManager` / `BucketManager`
  首次加载）会直接 500。
- **处理**：`support/vendor_patch.php` 把 4 个类的 5 处构造函数参数改成显式的
  `?Type $x = null`（语义完全等价），并由 `composer.json` 的 `post-autoload-dump` 在
  `composer install / update / dump-autoload` 之后自动重打；手工补打：
  `php support/vendor_patch.php`（幂等，上游修复后自动落空）。`vendor/` 不参与在线升级，
  补丁不会被覆盖。
- **顺带一提**：Composer 2.4 及更早的 phar 自身在 PHP 8.4 上也刷同类提示，那是 composer
  内部代码，与项目无关；用 PHP 8.3 跑 composer 即可安静。

## 二、登录与会话

### 2.1 登录返回 429「登录失败次数过多」

- `security.login_fail_limit`（默认 5）与 `security.login_fail_window`（默认 15 分钟）触发。
- 等待窗口过期，或在 Redis 删除 `cccms:login_fail:{小写用户名}`。
- 如需关闭限流，把 `security.login_fail_limit` 设为 `0`。

### 2.2 提示验证码错误 / 验证码一直不对

- 验证码**一次性使用**，校验后无论对错立即删除；点「刷新」会生成新的，旧的自然失效。
- 若 `security.login_captcha = 0`，前端不会展示验证码，`GET /auth/captcha` 返回 `null`。

### 2.3 操作过程中突然 401（登录失效）

可能原因：

| 原因 | 说明 |
|------|------|
| 令牌过期 | 达到 `security.token_ttl`（默认 2 小时）。**活跃用户不会遇到** —— 剩余不足 1/3 时后端经 `X-Refresh-Token` 自动换发，前端静默替换；停用超过 TTL 才需重新登录 |
| 用户被禁用 / 删除 | `CheckLogin` 每请求重建上下文，立即 401 |
| 开启维护模式 | `SessionGuard::cut()` 让非超管旧 token 失效（这是故意的 401，前端走既有逻辑跳登录页） |
| 服务端时间偏差 | JWT 校验含 `nbf` / `exp`，服务器时间需准确 |
| 分域部署未放行响应头 | 跨域时 `X-Refresh-Token` 需在 `Access-Control-Expose-Headers` 中，已默认声明；若前置网关改写了该头会导致续期失效 |

### 2.4 登出后旧 token 还能用

- **已修复**：登出会把当前 `jti` 写入 Redis 黑名单（TTL = 剩余有效期）并移除在线会话。
- 若仍能用，检查 Redis 是否可用 —— 失效名单在 Redis 不可用时**静默降级为不拦截**
  （`SessionGuard` / `LoginThrottle` 同一取舍：加固层不阻断业务）。应急手段：
  用「在线用户」页强制该用户下线，或修改 `JWT_SECRET`（所有 token 失效）。

### 2.5 强制下线了，对方还能操作

- 「下线」需要**两处同时生效**：`OnlineSession::remove*()`（从在线列表移除）+ `TokenBlacklist`
  （作废已发出的令牌）。
- 对方下一次请求就会 401；若他页面已加载，需要**刷新或下一次请求**才感知（前端会跳登录页）。
- 若完全无效果，先确认 Redis 可用（同上）。

### 2.6 无法强制下线自己

- 按设计拒绝：`OnlineLogic::kick()` / `kickUser()` 会校验当前用户 / 当前会话
  （`$request->jti`），否则操作者会被立刻踢出去。请使用用户下拉里的「退出登录」。

## 三、权限与菜单

### 3.1 接口返回 500「接口未声明权限」

- **原因**：`fail-closed` —— 控制器方法没有声明任何鉴权注解。
- **处理**：补 `#[Permission(...)]` / `#[NoAuth]` / `#[NoLogin]`，并执行 `php webman cccms:perm-scan`。

### 3.2 接口返回 403

- 当前角色没有被授予该 slug 的节点。
- 在「权限配置 → 角色管理」给角色勾上该节点并保存。
- 注意角色继承：子角色能用的节点 = 自身 ∪ 祖先链；授权界面里继承节点只读，需要去父角色上改。

### 3.3 接口返回 405 / 406

- 405：请求方法不在 `#[Restrict(methods: [...])]` 白名单内。
- 406：`?format=` 不在允许的编码集内（默认只允许 `json`）。

### 3.4 左侧菜单不显示某个页面

| 排查点 | 说明 |
|--------|------|
| `db/menu.php` 声明了吗 | 菜单（type=2）需在此声明，然后 `menu-sync` |
| 执行同步了吗 | `php webman cccms:menu-sync` |
| 角色授权了吗 | 菜单节点是权限节点，未被授权则 `userTree` 不返回 |
| `status = 1` 吗 | 菜单被停用则不展示 |
| 在回收站吗 | 软删的菜单不展示，`menu-sync` 会把声明文件里的节点恢复 |
| 前端组件名对吗 | 页面 `defineOptions({ name })` 必须等于菜单 slug |

### 3.5 按钮不显示

- 按钮由注解生成，执行 `php webman cccms:perm-scan` 后才会出现在 `sys_menu`。
- 检查 `v-auth` 里的 slug 是否与后端 `#[Permission(slug:)]` 完全一致。
- 检查角色是否被授予该按钮节点。

### 3.6 刷新页面永远 404

- **原因**：动态路由注册后，守卫里若写成 `{ ...to, replace: true }`，`to.name` 为 `notFound` 会因 name 优先被再次解析回兜底路由。
- **处理**：必须按 path 重新导航：`return { path, query, hash, replace: true }`（见 [09-前端开发规范 §4.3](09-前端开发规范.md#43-路由守卫beforeeach)）。
- 另外确认 404 路由**没有**标 `public`。

### 3.7 改了权限 / 菜单却不生效

- 角色与权限集合有 Redis 缓存（`PermissionCache`），但**任何 RBAC 变更都会 `bump()` 版本号**立即失效，
  正常情况应当是即时生效的。排查：

  | 排查点 | 说明 |
  |--------|------|
  | 节点生成了吗 | 新增接口后要执行 `php webman cccms:perm-scan` |
  | 菜单声明改了但没同步 | 执行 `php webman cccms:menu-sync`（或后台侧边栏用户卡片的「系统刷新 → 整体同步」） |
  | 前端菜单 / 权限缓存 | 侧边栏用户卡片「清理缓存」，或重新登录 / 刷新页面 |
  | Redis 不可用 | 权限缓存会「读不到也写不进」，退回实时查库，此时以 DB 为准 |

- 兜底手段：后台侧边栏用户卡片「清理缓存」（`PermissionCache::bump()`），
  或手工 `redis-cli incr cccms:auth:ver`。

## 四、数据权限

### 4.1 列表 / 详情查不到数据，甚至报「列不存在」

| 现象 | 原因 | 处理 |
|------|------|------|
| 报「列不存在」 | 模型参与数据权限，但表没有 `create_by` / `dept_id` 且未声明语义 | 在模型声明 `owner` / `dept`，或声明 `$dataScope = false`（详见 [06-数据权限](06-数据权限.md)） |
| 「自定义」档角色什么都看不到 | `data_scope = 5` 且没有命中规则 → `WHERE 1 = 0`（刻意 fail-closed） | 配置规则，或改用其它档位 |
| 「本部门」档看不到数据 | 用户未分配部门 → `dept_id IN (0)` | 给用户分配部门 |
| 部门树是空的 | 可见节点的父节点不在可见集合内 | 系统已做「提升为顶层」处理；若仍为空，检查部门数据本身 |

### 4.2 配了规则却不生效

| 排查点 | 说明 |
|--------|------|
| 表登记了吗 | 自定义规则只在**受控表**上生效；数据权限页「受控表」里登记 |
| 规则绑定命中了吗 | 绑定维度按 `bind_mode` 组合；角色绑定是**精确匹配**（不含子角色、不继承父角色） |
| 目标是超管吗 | 超管不受数据权限限制 |
| 规则体检说什么 | 规则列表「检测」列 / `php webman cccms:data-rule-check` |
| 角色档位是 1 吗 | `data_scope = 1`（全部数据）时**自定义行级规则不生效** |
| 取值完整吗 | `in` 空、`between` 少值会导致规则被静默跳过 |

### 4.3 绑定规则时看不到某个用户 / 部门

- 「绑定部门」候选项应是全量（`treeAll()`）；若被收窄，说明该处误用了带作用域的查询。
- 「绑定用户」搜索走 `withoutGlobalScope()`，应能拿到全量候选人。
- 若确有异常，检查 `ProfileLogic` / `DataRuleLogic` 是否仍存在裸查询（`cccms:data-scope-check` 会报）。

### 4.4 字段级规则的问题

| 现象 | 说明 |
|------|------|
| 掩码字段提交后又变回掩码值 | 正常：写入侧会剔除掩码字段，不会污染数据 |
| 密文字段显示乱码 | 前端需用 `decryptField(值, userStore.cryptoKey)` 解密 |
| `mask` + `encrypt` 叠加后是「被掩码的密文」 | 字段级动作**按 id 升序依次处理**，叠加结果如此；体检会提示 `field_dup` |

### 4.5 工作台数字与列表不一致

- 统计口径应与列表一致（按当前用户数据范围聚合）。
- 若不一致，检查 `DashboardLogic` 是否绕过模型做了全量计数（`data-scope-check` 会报）。
- **「某张统计卡不见了」是正常现象**：13 项计数各自绑定「能进对应列表页」的权限节点
  （如 `dept → cccms:dept:tree`、`log → cccms:log:index`），无权限时后端不下发该键、前端不渲染该卡，
  属于刻意的防越权设计。超管因 `hasPermission()` 直通，永远看到全部卡片。

## 五、前端

### 5.1 暗色模式下颜色错乱 / 某处颜色没跟随主题

- **原因**：组件里写死了颜色。
- **处理**：改用 `var(--art-*)` 或 `var(--el-*)`。主色变化必须经 `utils/theme.applyPrimary()`。

### 5.2 页面切换后状态没保留（keep-alive 失效）

- 页面必须用 `defineOptions({ name: '<菜单 slug>' })` 声明组件名，且与动态路由 `name`（= 菜单 node）一致。
- 关闭标签页会从 keep-alive 的 `include` 名单移除，属预期行为。

### 5.3 白屏 / 首屏卡住

- `main.ts` 对后台配置请求设置了 2.5 秒超时兜底，不应卡住；若白屏，看浏览器控制台报错。
- 检查 `VITE_API_BASE` 与代理配置。
- 检查 `index.html` 的首屏 loader 是否被移除（`app.mount` 前的异常会导致不移除）。

### 5.4 接口报错提示重复弹

- 响应拦截器已统一提示；页面 `catch` 里不要再弹一次。

### 5.5 回收站按钮点了没反应 / 列表没切数据

- `useRecycle` 必须写在 `useTable` **之前**。
- 列表接口要带上 `trashed: recycle.value ? 1 : 0`。
- 检查当前用户是否有 `cccms:recycle:restore` 或 `cccms:recycle:delete` 权限（`RecycleToggle` 用它控制显隐）。

### 5.6 导出没有反应 / 下载失败

- 当前**只有日志导出**（`GET /log/export`）在用这条链路；用户与数据权限规则的导入导出已下线，
  界面上找不到对应按钮是预期行为。
- 响应拦截器对 `responseType === 'blob'` 的请求**保留完整响应**（要读文件名），
  因此导出必须走 `downloadFile()`（见 [10-前端组件参考](10-前端组件参考.md#112-downloadfileapirequestts)），
  不要在页面里自己拼 `axios`。
- 403：当前角色没有 `cccms:log:export` 节点；`404`：后端未注册路由。

### 5.7 导出的 CSV 在 Excel 里中文乱码

- 正常情况不会：`support/Csv.php` 会在文件开头写入 **UTF-8 BOM**。
  若仍乱码，多半是中间层（网关 / 代理）改写了响应体或编码。
- 打开后发现单元格开头多了单引号（如 `'=1+1`）：这是**公式注入防护**，
  以 `= + - @` 开头的值会被前置单引号，Excel 按纯文本处理，属预期行为。

### 5.8 升级后角色授权树里还有「导出用户」这类按钮

- 这些是已下线功能的权限节点。`PermScanner::sync()` **只 upsert 不删除**，所以不会自动消失。
  跑一次 `php webman cccms:db-upgrade` 即可幂等清理（先删 `sys_role_node` 授权再删 `sys_menu` 行，
  并失效权限缓存）。详见 [11-常用命令与运维](11-常用命令与运维.md)。

### 5.9 用户头像上的「我的消息」角标不更新

- 角标在进入系统时拉取一次，并**在标记已读后刷新**；不会轮询。
- 若长时间不更新，刷新页面即可（或重新登录，`reset()` 会清空本地状态）。

## 六、定时任务

### 6.1 任务到点不执行

| 排查点 | 说明 |
|--------|------|
| 是 Linux 吗 | Windows 不支持自定义进程 |
| 调度进程在跑吗 | `php start.php status` 看 `crontab` 进程 |
| 任务启用了吗 | `status = 1` |
| 表达式对吗 | 六段（秒 分 时 日 月 周）；日与周同时限定按 AND；不做月份天数回绕 |
| 目标类合法吗 | 必须实现 `CrontabTask` 接口，且能被 `targets` 扫描到（放在 `plugin/*/command/task`） |
| 参数合法吗 | `params` 为对象 / JSON |

### 6.2 日志没被自动清理

- `seed.sql` 已预置一条指向 `LogCleanTask` 的任务（每天 03:00，分组「系统」）。
  若被删除或停用，需手工新增：执行目标选 `cccms/LogCleanTask`。
- 同时确认 `log.auto_clean = 1` 且 `log.keep_days > 0`（任一不满足，任务会**直接跳过**并说明原因）。

### 6.3 任务重复执行

- 调度器已按秒去重（`CronMatcher::markAndCheckHit`）。若仍重复，检查是否同时存在多条相同任务，或是否有多个调度进程实例。

### 6.4 执行日志里的「跳过 / 超时释放」是什么意思

| 状态 | 来源 | 含义 |
|------|------|------|
| `跳过`（status=2） | `overlap = skip` | 上一次执行尚未结束，本次不跑。该日志按任务**每 60 秒最多一条**（避免刷屏） |
| `超时释放`（status=3） | `timeout > 0` | 上次运行的锁已超过 `timeout` 秒，判定为卡死：**强制释放运行锁**并留痕，本次继续执行 |

> ⚠️ 超时**不能真正中断**卡住的代码（任务在同一进程内执行），只能解锁 + 留痕 + 让后续调度恢复。
> 需要硬超时请自行在任务内做分段 / 协作式检查。

### 6.5 任务失败后没有继续重试

- 重试由**作业队列**承担，不在调度进程里：失败后投递 `CrontabRetryJob`（队列 `crontab`，`available_at = 现在 + retry_interval`）。
  因此先看「定时任务 → 作业队列」tab：
  - **作业卡在「待执行」且心跳为「未心跳」**：`job_queue` 进程没起（Windows 上没有自定义进程，容器里 `php start.php start` 未拉起），
    重试不会发生。导出这类链路会回落到「下载时补生成」，定时任务的重试则**只能等队列进程恢复**。
  - **作业在「死信」**：进程被反复 kill（`max_attempts = 3` 用尽）。看 `last_error`，修好后点「重试」。
- 每轮执行完仍失败才会投递下一轮，`retry_times` 用尽即停；「重试次数」只记在任务配置里，与作业的 `max_attempts` 无关。
- 任务被**停用 / 删进回收站**后，排队中的重试直接作废（作业输出里是「跳过」）；删除任务时一并撤销。
- 重试执行记录仍是普通执行日志（`source = retry`），可在任务详情里看到。

## 七、附件与存储

### 7.1 上传失败

- 检查扩展名是否在白名单（`upload.ext_allow`）、大小是否超 `upload.max_size`。
- 本地驱动：检查 `server/public/storage` 是否可写。
- 云驱动：检查「配置管理 → 上传」中当前驱动对应的凭证是否齐全（切换驱动后页面只显示该驱动的字段）；未安装对应 SDK 会抛 500 并给出 composer 命令。

#### 报错 `tempnam(): file created in the system's temporary directory`（500）

**根因**：`php.ini` 的 `upload_tmp_dir` 指向了**不存在或不可写**的目录。Workerman 解析 multipart
上传时用 `tempnam(该目录)` 给每个文件落临时文件，目录无效时 PHP 回退到系统临时目录并抛一条
notice，而 webman 的全局错误处理器把任何 notice 都转成 `ErrorException`，于是上传直接 500。

**处理**（二选一，都做了最稳）：

1. **立即**：把 `upload_tmp_dir` 指向的目录创建出来并确保可写（或把它改成有效路径 / 置空）。
2. **长期**：本系统已内置 `UploadBootstrap` 启动引导 —— 启动时校验 `upload_tmp_dir`，
   无效则一律落到 `server/runtime/upload-tmp/`（应用自建、必然可写），
   因此**重启服务**后即使 ini 配错也不会再 500。

### 7.2 上传成功但图片 404

- 检查 `upload.url_prefix`（默认 `/storage`）与实际访问路径是否一致。
- 本地驱动下确认 Nginx / 后端能正确服务 `public/storage` 目录。
- 注意：切换存储驱动后，**历史文件不会自动迁移**。

#### 图片 / 附件返回 403

**根因**：本地存储的直链由 `StorageGuard` 判定，三种情况会 403（详见 [11-常用命令与运维 §6.2](11-常用命令与运维.md#62-安全)）。

| 现象 | 原因 | 处理 |
|------|------|------|
| 某个附件 403，其它正常 | 该附件被设为**私有**（`is_public = 0`） | 附件列表打开「公开」开关；或按业务需求走登录下载 |
| **所有**附件都 403 | 总开关「允许匿名访问附件」被关（`upload.anonymous = 0`） | 配置管理 → 上传 → 打开总开关 |
| **所有**附件都 403，开关也开着 | 请求没经过后端（Nginx 直接 `root` 托管 `/storage`） | 按 [02-安装部署 §5.2](02-安装部署.md#52-publicstorage-安全硬要求) 反代到后端；直接用 [nginx.conf.example](nginx.conf.example) |
| 页面里旧图裂开、新上传正常 | 该附件刚被改为私有，浏览器缓存的是旧响应 | 刷新页面；私有响应均带 `Cache-Control: no-store`，正常不会长期缓存 |
| 手工拷进 `public/storage` 的文件 403 | 不在 `sys_file` 里（上传是唯一写入口） | 走上传接口入库，不要手工放文件 |

> 云存储驱动（OSS / COS / 七牛）不经过本开关：URL 由云侧生成，访问控制应配私有 bucket + 云侧签名。

### 7.3 删除附件后物理文件还在

- 正常：软删除刻意保留物理文件，**彻底删除**时才清。
- 到列表右上角切「回收站」模式 → 彻底删除。

## 九、数据与升级

### 9.1 恢复回收站数据失败

- 唯一键占用：`user.username` / `role.code` / `post.code` / `dict_type.type` / `menu.node` 的值若已被其它记录占用，需先处理占用方。
- 上级仍在回收站：`dept` / `category` / `dict_data` / `menu` 需先恢复上级。

### 9.2 升级后报错（缺列 / 缺表）

- 执行 `php webman cccms:db-upgrade`（幂等补表 / 列 / 索引）。
- 若仍有问题，检查是否某业务插件未提供 `db/schema.sql`。

### 9.3 改了系统配置不生效

- 检查是否读的是硬编码而非 `SysConfig`。
- `SysConfig` 有 300s Redis 缓存，但保存后会 `flush()`；若直接改数据库而未经后台保存，需等 TTL 或手动删 `cccms:config:all`。

### 9.4 数据库结构与代码不一致（缺表 / 缺列）

- 执行 `php webman cccms:db-upgrade`（幂等）：补新增表 / 列 / 索引，并执行各业务插件的 `db/schema.sql`。
  新增列会先查 `information_schema` 再 `ALTER`，可重复跑（MySQL 8 不支持 `ADD COLUMN IF NOT EXISTS`）。
- 最近一次新增：`sys_log.action_id` / `session_id` / `hash_version` 及对应索引
  （链路按「一次操作」聚合 + 会话轨迹 + 哈希版本号）；此前还有
  `sys_notice` / `sys_notice_read` 两张表、`sys_log.type/status/message/trace_id`、
  `sys_crontab` 的 9 个增强列、`sys_crontab_log.source`。
- **直接从旧版本升级**时必须跑这条命令；全新安装导入 `schema.sql` 即可。
- 没跑升级时程序不会崩：`LogChain` 检测到新列缺失会降级为不带新列的普通写入（日志仍在，只是没有
  action / session 关联），但链路与哈希版本能力不可用。
- 本次同时新增权限节点 `cccms:log:action`（查看操作链路）与 `cccms:log:session`（查看会话轨迹），
  升级后需执行 `php webman cccms:perm-scan` 生成按钮节点，并在「角色管理」里授权（超管无需）。

| `server/runtime/logs/workerman.log` | 框架运行日志 |

| **响应头 `X-Trace-Id` / 失败响应体的 `trace_id`** | 一次**HTTP 请求**的 ID（后端生成）。用于定位单条记录，必要时 `/log/trace?trace_id=xxx` |

| `php webman cccms:data-scope-check` | 校验数据权限接入 |
| `php webman cccms:data-rule-check` | 体检数据规则冲突 |
| `php webman cccms:write-guard-check` | 校验写方法是否声明字段白名单（防 Mass Assignment） |

### 10.1 `cccms:log-verify` 报出断点怎么办

按 `reason` 分三类，处置方式不同：

| reason | 含义 | 处置 |
|--------|------|------|
| `content_modified` | 该行内容与入库时的哈希不符 | 基本可判定**被直接改库**。先留证据（`SELECT *` 存下来），再核对操作日志与该 id 时间段的运维动作 |
| `link_broken` | 后一行的 `prev_hash` 接不上前一行 | 中间有行被删。**先确认不是应用自己删的**（管理员删日志 / `log-archive` / `log-clean` 都会调 `LogChain::reanchor()` 前移起点；链**中间**的删除无法与篡改区分） |
| `tail_stale` | 链状态表记的链尾与实际最后一行不符 | 尾行被删或替换。查 `sys_log_chain` 的 `update_time` 定位大概发生时间 |
| `chain_missing` | 链上有记录但状态行没了 | `sys_log_chain` 的整行被人删掉。库权限本身已失守，按安全事件处理 |

> 排除误报：**未纳入链的行**（`row_hash` 为空，含本能力上线前的历史数据与链表不可用时的降级写入）
> 只统计不报错；升级后请执行一次 `php webman cccms:db-upgrade` 补齐列与表。
