# 数据权限

> 数据权限回答「同一个接口，不同的人能看到 / 修改哪些数据」。CCCMS 把它下沉到服务层：查询统一调用 `apply_scope()`，由角色档位与规则生成租户内的收窄条件。

---

## 一、三个层次

| 层次 | 作用 | 实现位置 |
|------|------|----------|
| 租户隔离 | 只能看到本租户数据 | `apply_scope()` 的 `tenant_id` 条件，不可放宽 |
| 角色档位 | 按「全部 / 部门 / 本人 / 自定义」收窄 | `sys_role.data_scope` |
| 自定义规则 | 行级条件、字段可见性 | `sys_data_rule` + `sys_data_scope_table` |

三者是**叠加**关系：租户条件是硬边界，档位生成基线，行级规则再 AND 上去。

---

## 二、模型声明

在服务模块导入时声明一次：

```python
from cccms.core.scope import ScopeConfig, apply_scope

User.__data_scope__ = ScopeConfig(owner=_user_owner, dept=_user_dept)

statement = apply_scope(select(User), User)
```

`ScopeConfig` 字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `owner` | 列名或 `(model, user) -> 条件` | 「仅本人」的判定；无此列时用回调 |
| `dept` | 列名或 `(model, dept_ids) -> 条件` | 「本部门」的判定；无此列时用回调 |
| `no_baseline` | `bool` | 跳过档位基线，只叠加自定义规则 |

当前声明：

| 表 | 模型 | owner（仅本人） | dept（本部门） | 说明 |
|----|------|-----------------|----------------|------|
| `sys_user` | `User` | `id` | 经 `sys_user_dept` 取成员 | 参与 |
| `sys_dept` | `Dept` | 我所属部门 | 部门子树 | 参与 |
| `sys_file` | `FileRecord` | `create_by` | 经 `create_by` → `sys_user_dept` | 参与 |
| `sys_log` | `OperationLog` | `user_id` | 部门成员 | 参与 |
| `sys_crontab` | `Crontab` | — | — | `no_baseline=True` |
| `sys_role` / `sys_post` / `sys_data_rule` | — | — | — | 不参与 |
| `sys_notice` | — | — | — | 阅读侧按投放对象过滤 |

约定：

- 超管不受数据权限限制，但仍受租户硬边界。
- `apply_scope(..., include_deleted=True)` 用于回收站。
- 唯一性与存在性校验使用不带范围的查询，避免「看不见就当没重复」。
- 新增业务表必须显式声明 `ScopeConfig`；没有 `create_by` / `dept_id` 的表用 `no_baseline=True`。

> ⚠️ **注意**：`apply_scope()` 是显式调用，不是 ORM 全局钩子。新写查询时忘记调用不会被框架兜底，这是刻意的取舍（避免登录、调度等无租户上下文被误加条件）。

## 三、角色档位

| 值 | 含义 | 行为 |
|----|------|------|
| 1 | 全部数据 | 不加任何条件；**自定义行级规则也不生效** |
| 2 | 本部门及以下 | 部门基线 + 自定义规则（AND） |
| 3 | 本部门 | 本部门基线 + 自定义规则（AND） |
| 4 | 仅本人 | owner 基线 + 自定义规则（AND） |
| 5 | 自定义 | 不加基线，只用自定义行级规则 |

补充规则：

- **多角色取最严**：`max(data_scope)`。任一角色的宽范围不得静默放大整个账号；需要放宽时应显式调整角色档位，而不是靠多挂一个角色。无角色时退化为 4（仅本人）。
- **只按直连角色计算**：不含祖先角色，避免父角色的「全部数据」变成隐式提权通道。
- **无角色退化为 4（仅本人）**；新建角色列默认值也是 4。
- **档位不继承**：角色继承只传递权限节点，不传递数据范围。
- **超管不受限**。

> ⚠️ **`data_scope=5` 的语义**：没有规则或一条都没命中 → `WHERE 1 = 0`，看不到任何数据。这是 fail-closed：某张表不该隔离时，应声明 `ScopeConfig(no_baseline=True)` 或不声明，而不是靠「没规则」放行。

## 四、行级规则

一条规则由「绑定对象 + 条件」组成。

| 字段 | 说明 |
|------|------|
| `name` | 规则名 |
| `user_id` / `post_id` / `role_id` | 绑定用户 / 岗位 / 角色；`0` = 不限 |
| `dept_ids` | 绑定部门（JSON 数组），**含下级** |
| `bind_mode` | 维度组合：`or`（默认，任一命中）/ `and`（已填项全部命中） |
| `table_name` | 目标表；为空表示不限表 |
| `action` | `row` / `hidden` / `readonly` / `mask` / `encrypt` |
| `field` | 字段级动作必填 |
| `operator` | 行级操作符 |
| `value` | 取值，逗号分隔，可混用动态变量 |
| `value_type` | `static` / `dynamic` |

### 4.1 维度组合

- 单条规则内：`or` 命中任意一项即生效；`and` 要求所有**已填写**维度命中，未填写维度不参与。
- 四个维度都为空 = 全局规则。
- 多条规则之间是 **AND**：每条命中的规则各加一个条件，只会更窄。
- 规则按 `id` 升序执行，顺序不影响行级结果。

> ⚠️ **陷阱**：`or` 比直觉宽。同时绑定「用户 A」和「岗位 P」表示「A 或所有 P 的人」，不是「A 且属于 P」。需要后者请改为 `and`。

### 4.2 操作符

`=` `!=` `<>` `>` `>=` `<` `<=` `like` `in` `between`

- 字段名必须匹配 `[A-Za-z_][A-Za-z0-9_]*`。
- 取值全部参数化，封死注入面。
- `in` / `between` 取值不完整时规则被跳过。

### 4.3 动态变量

| 变量 | 含义 |
|------|------|
| `{user.id}` | 当前用户 ID |
| `{dept.ids}` | 我所属部门 ID |
| `{dept.subtree}` | 我所属部门及子树 |
| `{post.ids}` | 我的岗位 |
| `{role.ids}` | 我的有效角色（直连 + 祖先） |

可与字面量混用，如 `{user.id},100,101`。展开为多值时，标量操作符按「属于」处理。

> **角色口径**：规则绑定角色与 `{role.ids}` 使用**有效角色**（含祖先）；档位只使用**直连角色**。

## 五、字段级规则

| 动作 | 出参 | 写入 |
|------|------|------|
| `hidden` | 字符串置空，其它类型置 `None` | 字段被忽略 |
| `readonly` | 原值返回 | 字段被忽略 |
| `mask` | 掩码（手机号前 3 后 4、证件号前 4 后 4、其它首尾各 1/3） | 字段被忽略 |
| `encrypt` | 当前按掩码展示（前端解密 helper 已具备，页面尚未接入） | 字段被忽略 |

实现：

- 出参：`core/scope.py::apply_field_actions()` 在 `_to_out()` / `_to_node()` 中就地改写，保持响应模型结构不变。
- 入参：`blocked_write_fields()` 让更新逻辑跳过被规则命中的字段，避免「掩码值回填污染数据」。
- 已接入模块：用户、部门、附件、操作日志。
- 解密密钥只在 `may_decrypt_fields=true` 时下发（超管或拥有 `cccms:data_rule:save` / `cccms:data_rule:update` 的角色）。

> ⚠️ **注意**：`encrypt` 当前只做**展示层遮蔽**，不等于数据库列加密，也不构成访问控制。真正的访问控制是行级规则与权限节点。

> 待补充：其他业务表接入字段级规则时，需在对应 `_to_out()` 调用 `apply_field_actions()`，并在写入逻辑中过滤 `blocked_write_fields()`。

## 六、受控表

`sys_data_scope_table` 登记「允许配置自定义规则」的表。

- 未登记的表仍受档位基线保护，只是不能配自定义规则。
- 行级规则只有在 `table_name` 已登记且 `status=1` 时才生效。
- 受控表列表返回 `field_count` 与 `exists`：表被改名或删除时 `exists=false`，规则会暂停生效。
- 仍有规则引用的受控表不允许删除。

---

## 七、边界语义

| 场景 | 结果 |
|------|------|
| 档位「本部门」但用户没有部门 | 看不到任何数据 |
| 档位 5 且没有命中规则 | 看不到任何数据 |
| 规则字段不存在 / 操作符非法 | 该条规则被跳过 |
| 超管 | 跳过档位与规则 |
| 无租户上下文（登录、调度） | `tenant_clause` 返回空，不加租户条件 |
| `without_scope("原因")` | 显式豁免，必须写原因 |

> **提示**：`without_scope` 是逃生舱，只应用于确有必要的系统级查询；滥用会让数据权限形同虚设。

---

## 八、接入新表

1. 模型继承 `BaseModel` / `TenantMixin`。
2. 在对应服务模块导入时声明 `__data_scope__`。
3. 所有列表、详情、写操作前的可见性校验都使用 `apply_scope()`。
4. 在「数据规则 → 受控表」登记表名（需要自定义规则时）。
5. 出参调用 `apply_field_actions()`，写操作过滤 `blocked_write_fields()`。
6. 补一条「看不到就不能改」的用例。
