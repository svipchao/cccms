# 数据权限

> 数据权限回答「同一个接口，不同的人能看到 / 修改哪些数据」。CCCMS 把它**下沉到模型层**：只要查询走模型就自动生效，不依赖开发者记得手写。本文讲清楚五档范围、行级 / 字段级规则、受控表、边界语义与接入步骤。

---

## 一、先厘清三个概念

这三者经常被混为一谈，必须分开：

> 字段级语义与索引见 [13-数据模型 §四](13-数据模型.md#四数据权限)（`sys_data_rule` / `sys_data_scope_table`）。

| 概念 | 含义 | 决定方 |
|------|------|--------|
| **模型化** | 该表查询改走 `Model` 而不是 `Db::name()` | 各模块迁移进度 |
| **参与数据权限** | 是否按预设基线（仅本人 / 本部门）收窄 | 模型里的 `$dataScope` 声明 |
| **登记受控** | 是否可配**自定义**行级 / 字段级规则 | `sys_data_scope_table` |

关键结论：

- **模型化 ≠ 参与数据权限**：一个模型可以查询全走模型但声明 `$dataScope = false`（如角色表）。
- **参与基线 ≠ 登记受控**：未登记受控的表仍受预设基线保护，只是不能配自定义规则。
- **登记受控 = 纳入检查**：`cccms:data-scope-check` 会把登记的表作为受控表检查其查询是否走模型。
- **多租户在本文之外再套一层硬边界**：租户条件（`tenant_id`）是**最外层**作用域，
  **任何档位都无法放宽**；也就是说档位 1「全部数据」= **本租户**全部数据。详见 §十二。

## 二、角色级预置范围（`sys_role.data_scope`）

| 值 | 含义 | 行为 |
|----|------|------|
| 1 | 全部数据 | 不加任何条件；**自定义行级规则也不生效** |
| 2 | 本部门及以下 | 先加「本部门 + 子树」基线，**再叠加**自定义规则（AND） |
| 3 | 本部门 | 先加「本部门」基线，再叠加自定义规则（AND） |
| 4 | 仅本人 | 先加「仅本人」基线，再叠加自定义规则（AND） |
| 5 | 自定义 | **不加预设基线**，只使用自定义行级规则 |

补充规则：

- **多角色取最宽松**（`min`）。用户有多个角色时，按范围最宽的那个角色取。
- **只按直连角色计算**（不含祖先角色）—— 与「规则绑定角色走有效角色」是刻意的差别：
  档位若跟随祖先，子角色会因父角色的「全部数据」而隐式扩权。
- **无角色退化为「仅本人」**（等价 `data_scope = 4`）。
- **档位不继承父角色**（定案）：角色继承只传递**权限节点**，不传递 `data_scope`。
  子角色若需要更宽的范围，必须在自己身上显式设置 —— 若跟随祖先，父角色的「全部数据」
  会把子角色的授权变成**隐式提权通道**，且排查越权时无法从子角色本身看出范围来源。
- **列默认值 `4`（仅本人）**：档位靠「取最宽松」生效，漏配时必须是**最窄**兜底，
  否则新建角色会静默拿到全库可见范围（`sys_role.data_scope` 的 `DEFAULT 4`）。
- **超管不受数据权限限制**。

> ⚠️ **`data_scope = 5` 的语义要特别注意**：没有配规则、或一条都没命中 → **看不到任何数据**（`WHERE 1 = 0`）。这是刻意设计：模型参与数据权限就说明这张表按范围隔离，此时「没有规则」只能是「无权限」。某张表压根不该隔离的正确做法是模型声明 `$dataScope = false`，而不是靠它没登记受控表来兜。

### 2.1 决策记录：档位是否继承父角色（定案：**不继承**）

角色继承在 CCCMS 里**只传递权限节点**（见 [05-鉴权与权限 §6.2](05-鉴权与权限.md#62-角色继承方案-a子角色继承父角色)）。档位（`data_scope`）是**数据边界**，与「能不能进这个菜单」不是同一类东西，因此刻意与节点继承解耦。决策时的两面权衡如下：

**选择「继承父角色」**

| 优点 | 缺点 |
|------|------|
| 子角色自动获得祖先的数据视野，配置省心 | **隐式扩权**：父角色为「全部数据」时，任何新建子角色都自动拿到全库 |
| 层级模型直观：档位随角色树传播 | 权限难审计：某子角色为何能看到某部门数据，需沿继承链回溯 |
| 子角色是父角色子集的场景几乎零配置 | 改父角色档位会**连带改所有后代**的实际权限，影响面不可控 |
| | 多级继承下档位语义需另立规则（取 max / min / 覆盖？），易生歧义 |
| | 与最小权限原则冲突：继承档位相当于把「授权」变成「提权通道」 |

**选择「不继承」（本仓库定案）**

| 优点 | 缺点 |
|------|------|
| **fail-closed**：祖先一律不参与，杜绝隐式扩权 | 父角色想统一收窄子角色视野时无法靠继承，须逐角色配置 |
| 语义清晰：角色数据视野 = 它自己的档位，断言与审计一目了然 | 新增子角色漏配时会落到默认档位**仅本人（4）**，容易被误读为「权限缺失」 |
| 行为可预测：改父角色档位不影响任何子角色 | 「子角色天然享有父角色数据」的诉求需手动重复配置同档位 |
| 与「列默认值 4（仅本人）」的兜底方向一致，漏配最坏结果是收窄而非泄漏 | |

**落地实现**（`support/DataScope.php::plan()`）：

- 档位：只取**直连角色**（`sys_user_role`）中范围最宽的 `min(data_scope)`；无角色 → 4。
- 有效角色（`effectiveRoleIds()` = 直连 + 祖先）：**仅**用于「行级 / 字段级规则绑定角色」与 `{role.ids}` 取值。
- 若将来确有「子角色必须天然享有父角色数据」的具体业务，正确做法是**给那部分角色显式设置档位**，而不是改这条全局规则。

## 三、按表声明语义（`$dataScope`）

每张表的「数据范围怎么算」写在模型里。`BaseModel::$dataScope` 三种取值：

| 取值 | 含义 |
|------|------|
| `false` | **不参与**数据权限（基础设施与组织架构数据） |
| `[]`（默认） | **参与**，按默认约定：`owner = create_by`、`dept = dept_id` |
| 数组 | 参与，并**覆盖**约定：`owner` / `dept` / `no_baseline` |

`owner` 支持三种写法：

| 写法 | 语义 | 示例 |
|------|------|------|
| 字符串（列名） | 「仅本人」= 该列等于当前用户 id | `['owner' => 'create_by']` |
| 字符串 `'id'` | 「仅本人」= 只看自己这个账号 | `['owner' => 'id']`（`User` 模型） |
| 回调 `callable($query, UserContext $user)` | 语义不是「某列等于我」时自行处理（**需自行 fail-closed**） | `Dept`：仅本人 = 我所属的部门 |

`dept` 回调收到的是**已展开好的部门 id 列表**（不传则默认 `whereIn('dept_id', $ids)`，适用于带 `dept_id` 列的业务表）。

`no_baseline = true` 表示**跳过预设基线**，只叠加自定义规则 —— 适用于既无 `owner` 又无 `dept_id` 列的业务表（如 `sys_crontab`、插件表 `ks_*`）。

### 3.1 各表现状

| 功能模块 | 表 | 模型 | owner（仅本人） | dept（本部门） | 声明 | 登记受控 |
|---|---|---|---|---|---|---|
| 用户管理 | `sys_user` | `User` | `id` | 经 `sys_user_dept` | 参与 | 已登记 |
| 部门管理 | `sys_dept` | `Dept` | 我所属部门 | 部门子树 | 参与 | 已登记（可撤销） |
| 附件管理 | `sys_file` | `File` | `create_by` | 经 `create_by` → `sys_user_dept` | 参与 | 已登记 |
| 定时任务 | `sys_crontab` | `Crontab` | — | —（`no_baseline`） | 参与 | 已登记 |
| 操作日志 | `sys_log` | `OperationLog` | `user_id` | 可见部门成员 | 参与 | 已登记 |
| 角色管理 | `sys_role` | `Role` | — | — | 不参与 | 不登记 |
| 岗位管理 | `sys_post` | `Post` | — | — | 不参与 | 不登记 |
| 数据权限规则 | `sys_data_rule` | `DataRule` | — | — | 不参与 | 不登记 |
| 菜单 / 配置 / 字典 / 分类 / 关联表 | — | — | — | — | 不参与 | 不登记 |

> **为什么 `sys_data_rule` 不参与**：否则管理员可能看不到自己配的规则。同理 `sys_role` 不登记受控（不出现在「目标表」下拉里）。

> **`sys_dept` 是可登记可不登记的典型**：不登记也受预设基线保护（「本部门及以下」档下部门管理页只见自己子树）；登记后才会出现在「目标表」下拉里，可配自定义规则。给部门配字段级规则（如隐藏 `name`）会让部门树显示空白名，配之前想清楚。

### 3.2 不声明会怎样

不声明 `$dataScope` 又确实没有 `create_by` / `dept_id` 列的表，查询会直接报「**列不存在**」——这是**有意的**：逼你把「这张表的数据范围怎么算」写清楚，而不是静默放行。

## 四、自定义规则 `sys_data_rule`

一条规则由「**绑定对象** + **动作** + **条件**」组成，同时支持行级与字段级。

### 4.1 字段说明

| 字段 | 说明 |
|------|------|
| `name` | 规则名 |
| `user_id` / `post_id` / `role_id` | 绑定用户 / 岗位 / 角色；`0` = 不限 |
| `dept_ids` | 绑定部门（JSON 数组，多选、跨部门）；**含下级** |
| `bind_mode` | 单条规则内部四个维度的组合方式：`or`（默认，任一命中）/ `and`（已填写的全部命中） |
| `table_name` | 目标表（不含前缀）；**空 = 不限表** |
| `action` | `row`（行级）/ `hidden` / `readonly` / `mask` / `encrypt`（字段级） |
| `field` | 字段名（字段级动作必填） |
| `operator` | 行级操作符（`row` 时使用） |
| `value` | 行级取值（逗号分隔，可混用动态变量） |
| `value_type` | `static`（静态） / `dynamic`（动态变量） |

### 4.2 绑定维度与组合方式

**单条规则内部**：

- `or`（默认）：命中**任意一项**即生效。
- `and`：**所有已填写**的维度都要命中；**未填写的维度不参与判断**（否则只填一项时永远不会命中）。
- 四项都空 = **全局规则**（对所有非超管生效）。

> ⚠️ **陷阱**：`or` 比直觉更宽。同时选「用户 A」+「岗位 P」是「A」**或**「所有 P 的人」，不是「A 且 处于 P」。要后者请把「绑定关系」改为「全部命中（且）」。

**多条规则之间**：

- 命中当前用户的每条行级规则，**各往查询里加一个条件** → 规则之间是 **AND**。
- 因此多条收窄规则叠加只会更窄；某条不命中的规则不参与，也不会放宽其它规则。
- 规则**先后顺序不影响行级结果**。
- ⚠️ 但两条语义相反的行级规则会把人过滤成「什么都看不到」（`WHERE id = 1 AND id != 1`）——安全但静默，用规则体检可以发现。

**字段级动作是按顺序依次处理**的：同一字段被多条字段级规则命中时，结果取决于处理顺序。运行时固定按规则 **id 升序**（创建顺序）执行，因此可复现。`mask` + `encrypt` 叠加会产出「被掩码的密文」，规则体检会提示。

> 规则**没有排序字段**：它不影响规则如何生效，列表固定按 id 升序输出，页面上也不展示。

实测口径（规则统一把 `user` 表收窄成 `id = 1`，命中即可见 1 行）：

| 场景 | `or` | `and` |
|------|------|-------|
| 无规则 | 0 | 0 |
| 只绑「自己有的岗位」 | 1 | 1（未填项不参与） |
| 「别人」+「自己的岗位」 | 1 | 0 |
| 「自己」+「自己的岗位」 | 1 | 1 |
| 四项全绑但角色绑错 | 1 | 0 |
| 四项都不填（全局） | 1 | 1 |
| `bind_mode` 非法值 | 按 `or` 兜底 | — |

### 4.3 行级操作符白名单

`=` `!=` `<>` `>` `>=` `<` `<=` `like` `in` `between`

- 字段名正则限 `[A-Za-z_][A-Za-z0-9_]*`。
- 取值全部参数化，封死注入面。
- `in` / `between` 取值用逗号 / 区间表达；取值不完整（`in` 空、`between` 少值）会导致规则被静默跳过，体检会提示。

### 4.4 字段级动作

| 动作 | 出参 | 入参（写入） |
|------|------|--------------|
| `hidden` | 字段不返回 | 剔除 |
| `readonly` | 照常返回 | **强制剔除**（看得见改不了） |
| `mask` | 掩码（如 `138****8888`） | 剔除 |
| `encrypt` | AES-256-GCM 密文（前端解密；密钥**仅下发给管理员**，且它是存储加密**不是**访问控制，见 [§11.1](#111-安全边界encrypt-是存储加密不是访问控制)） | 剔除 |

- 落点都在**模型层**：出参由 `BaseModel::toArray()` 统一处理，入参由 `ScopedQuery`（`BaseModel::$query`）在写库前剔除全部四种动作。
- 因此「掩码值被表单原样回填」不会污染数据；「看不见真实值 ⇒ 一定改不了」。
- 掩码规则：`phone/mobile` → 前 3 后 4；`id_card/idcard` → 前 4 后 4；其它 → 首尾各保留 1/3。

### 4.5 动态取值变量（`value_type = dynamic`）

按当前用户解析：

| 变量 | 含义 |
|------|------|
| `{user.id}` | 当前用户 id |
| `{dept.ids}` | 我所属部门 id 列表 |
| `{dept.subtree}` | 我所属部门及子树 id 列表 |
| `{post.ids}` | 我的岗位 id 列表 |
| `{role.ids}` | 我的**有效角色** id 列表（直连 + 祖先，与鉴权同口径） |

- 取值按逗号拆分，可与字面量混用，如 `{user.id},100,101`。
- 展开为多值时，标量操作符按「属于」处理（自动变 `whereIn`）。

> **角色口径说明**：规则的**绑定角色**与 `{role.ids}` 都用「**有效角色**」（直连 + 祖先，与鉴权同口径），
> 所以把规则绑到父角色，只拥有子角色的用户**会**命中 —— 与部门绑定的「含下级」直觉一致。
> 但角色的**档位** `data_scope` 只按**直连角色**取最宽松值（见 [§二](#二角色级预置范围sys_roledata_scope)），
> 不跟随祖先：否则子角色会因父角色的「全部数据」而**隐式扩权**。

## 五、fail-closed 的边界语义

| 场景 | 结果 |
|------|------|
| 声明「本部门」但用户没有部门 | `dept_id IN (0)` → 看不到任何数据 |
| `data_scope = 5` 且没有规则 / 一条都没命中 | `WHERE 1 = 0` → 看不到任何数据 |
| 模型声明参与，但表无对应列且未声明语义 | 报「列不存在」（提示你把语义写清楚） |
| 唯一性 / 存在性校验 | 用 `withoutAllScopes()` 看全量（唯一键**全局唯一**，含跨租户；否则「看不见就当没重复」会写出脏索引） |

作用域实现的四条铁律：

1. **表名以模型为准**：`applyToModelQuery()` 强制用 `$model->getName()` 覆盖声明里的表名，声明写错不影响实际表。
2. **用户上下文只从 `request()->user` 取**，不新建静态容器（非 fiber 环境下 `Workerman\Coroutine\Context\Fiber` 会写进 worker 级全局，导致跨请求身份泄漏）。
3. **无用户 ⇒ 不作用域**（fail-open，但边界封闭）：只剩登录链路、CLI、`#[NoLogin]` 三类场景，受保护路由会先被 `CheckLogin` / `CheckAuth` 拦下。
4. **租户条件不放进 `DataScope`**：它是独立的最外层作用域，详见 §十二。

## 六、逃生口（显式跳出作用域）

能用模型的地方优先用模型；需要看**全量**数据时显式跳出。

两个逃生口**语义不同**，选错就是越权漏洞（详见 §十二）：

| 写法 | 跳出的作用域 | 用在哪 |
|------|--------------|--------|
| `Model::withoutGlobalScope()` | 只跳出**数据权限**，**保留租户条件** | 默认选择：只想去掉档位收窄，不希望跨租户 |
| `Model::withoutAllScopes()` | 跳出**全部**作用域（含租户） | 仅登录链路 / CLI / 迁移 / **全局唯一键查重**，必须写清理由 |

| 场景 | 写法 |
|------|------|
| 唯一性 / 存在性校验（唯一键**全局唯一**） | `User::withoutAllScopes()->where(...)`（**不能**用 `withoutGlobalScope()`：它仍带租户条件，会漏查其他租户的占用） |
| 配置界面的候选项（如「绑定部门」下拉） | `DeptLogic::treeAll()` / `withoutGlobalScope()`（保留租户 = 只能选本租户数据，符合预期） |
| 回收站、操作已删行 | `Model::onlyTrashed()` / `Model::withTrashed()`（**两者都不解除租户限制**，要先跳出再配 `withTrashed()`） |
| 登录链路（还没有当前用户） | `User::withoutAllScopes()`（用户名全局唯一，登录不解析租户） |
| CLI（定时任务、命令、迁移）、`#[NoLogin]` 路由 | 自动跳过（无当前用户 ⇒ 不作用域） |

> 设计原则：**显式写出来，好过隐式生效**。逃生口必须能从代码上看出来，并注明理由。

## 七、规则体检（`RuleConflict`）

`cccms:data-rule-check` 与规则列表的「检测」列共用 `support/RuleConflict.php`，检查四类问题：

| 类别 | 含义 | 严重度 |
|------|------|--------|
| `row_unsat` | 行级条件互斥 → 命中者看不到任何数据 | 错误（命令退出码 1） |
| `field_dup` | 同字段多个字段级动作（按序叠加，非取最严） | 提示 |
| `never_hit` | 取值不完整（`IN` 空 / `BETWEEN` 少值）→ 规则被静默跳过 | 提示 |
| `not_guarded` | 目标表未登记受控表 → 规则不会执行 | 提示 |

**判定原则**：只报可证明为空的组合，宁可漏报不误报。

- 只比较**同绑定项**的规则，或含**全局规则**的组合。
- 只处理静态取值；`like` 与非数字比较一律跳过。
- 用**约束求交**（`in` 当集合、`between` 当区间、`!=` 当排除集），能抓到「三条规则两两有交集、合起来为空」的组合。
- 不同绑定项（如「部门 A」vs「岗位 P」）需要查用户全量才能判定，**不检**。

## 八、接入检查（`DataScopeChecker`）

`cccms:data-scope-check` 是静态代码检查，防止「登记了受控、查询却没走模型」的静默失效：

| 规则 | 内容 |
|------|------|
| R1 | `app/controller/**` 不得出现 `Db::name` / `Db::table` / `Db::query`（查询必须下沉到 Logic） |
| R2 | 登记在 `sys_data_scope_table` 的表：① 必须有模型且不得声明 `$dataScope = false`；② Logic 层不得再用 `Db::name('该表')` 查询 |
| R3 | 业务插件表（插件 `db/schema.sql` 声明、不带 `sys_` 前缀）必须「登记受控表 / 自带 `tenant_id` / 显式豁免」三选一，否则报错 |
| R4 | 模型声明 `$tenantScope = true` 的表必须在 `TenantContext::TABLES` 里，否则模型查询与直查路径结果不一致 |

- 自动发现业务插件（以 `db/menu.php` 为判定）。
- 主代码里找不到模型的受控表**只报 NOTICE 不报错**：如 `sys_data_scope_table` 里下游插件登记的 6 张 `ks_*` 表，本仓库是基础系统、不负责它们的 Logic，CI 不会被它们卡住 —— 这些表由 R3 强制「登记或豁免」。
- **R3 为什么必须报错**：插件表默认没有 `tenant_id`、也没登记受控表，此时租户不隔离、配好的规则也不生效，**界面上一切正常**。把「忘配」从静默放行变成退出码 1，是唯一能让它被发现的时机。
- **豁免**：确实不需要隔离的表（纯字典 / 归档 / 外部同步游标）写进 `DATA_SCOPE_EXEMPT_TABLES`（逗号分隔的完整表名）。豁免等于**明确接受跨租户可见**，应在评审中可见。
- 只判定**库里真实存在**的插件表：插件声明了但尚未建表不报错。
- 存在 `error` 级问题 → 命令退出码 1，可接 CI。

## 九、性能：请求级 scope plan

`DataScope` 在**每个请求内只解析一次**用户维度数据（角色 / 岗位 / 部门 / 规则 / 受控表），缓存实现：

```php
private static ?WeakMap $plans;   // 键 = UserContext 实例
```

- **用实例而不是 userId 作键**：Webman 常驻进程下，静态数组会跨请求存活（权限变更不生效）；`UserContext` 每请求由 `CheckLogin` 重建，`WeakMap` 随其回收自动释放，天然是请求级缓存，也避免 `spl_object_id` 复用串数据的风险。
- 实测：同一请求内 10 次模型查询，数据权限相关 SQL **0 条**（去掉缓存对照为 50 条）。

## 十、新插件接入（三步）

1. **模型声明**：代码生成器产出的模型已自带声明；手写模型要么参与（声明 `owner` / `dept`），要么显式 `protected $dataScope = false;`。
2. **插件表接入隔离**（R3）：建表时加 `tenant_id` 列（最稳），或登记受控表并配「租户 = 当前租户」的规则；确实不需要的写进 `DATA_SCOPE_EXEMPT_TABLES`。
3. **租户口径对齐**（R4）：模型声明 `$tenantScope = true` 时，把表名加进 `TenantContext::TABLES`（直查路径靠它）。
4. **登记受控表**（只有需要配自定义规则时才要）：数据权限规则页 →「受控表」→ 添加；或在插件的 seed 里 `INSERT`。
5. **跑检查**：`php webman cccms:data-scope-check`。控制器直连库、受控表未模型化、Logic 里裸查受控表、插件表未接入隔离都会报错。

此外，`php webman cccms:data-rule-check` 用于体检规则本身的冲突。

> **如何撤销登记**：数据权限规则页 →「受控表」→ 删除该行。规则不会丢，只是暂停生效。

## 十一、前端：字段级 `encrypt` 的解密

- 后端 `encrypt` 字段返回 `base64(iv(12) || tag(16) || cipher)`。
- 登录后 `GET /auth/me` 返回 `crypto_key`（`Cipher::publicKey()`，base64 公钥种子），前端保存在 `userStore.cryptoKey`。
- 用 `frontend/src/utils/crypto.ts` 的 `decryptField(encoded, keyBase64)`（WebCrypto AES-256-GCM）解密。

### 11.1 安全边界：`encrypt` 是存储加密，**不是**访问控制

**先看结论**：`crypto_key` 是 **AES-256-GCM 的对称密钥本身**（base64 后的公开形式），不是公钥。任何人拿到它就能解密**全部** `encrypt` 密文。

| 它能防 | 它**不能**防 |
|--------|--------------|
| 数据库被裸读（拖库 / 备份泄露）时直接看懂敏感值 | 接口泄露：密文与密钥同路下发，拿到响应就能解密 |
| 运维误查库时的肉眼可见 | 前端被查看：密钥就在浏览器内存 / store 里 |
| | 越权读取：能否取到该字段由**行级 / 字段级其它动作**决定，与 encrypt 无关 |

**因此**：

- 敏感字段的**访问控制**请用 `hidden`（不返回）/ `mask`（脱敏返回）+ 角色数据档位，不要指望 `encrypt`。
- `crypto_key` 的下发已收敛为**持有 `cccms:data_rule*` 权限节点的管理员与超管**（`AuthLogic::mayDecryptFields()`）：
  普通账号的 `/auth/me` **不含**该字段。规则配置页在选择 `encrypt` 动作时会展示同样的风险提示。
- 若确实需要「服务端解密后按数据权限下发」，属于**另立方案**（前端不再持有密钥），需单独评估工作量。

> ⚠️ 不要在无鉴权接口返回 `crypto_key`；也不要把 `encrypt` 当成端到端加密。

## 十二、多租户：租户是硬边界，档位是租户内的软范围

多租户采用**单库共享表 + `tenant_id` 列**：`tenant_id = 0` 为**平台租户**（虚拟，不落库），
真实租户存 `sys_tenant`（`id >= 1`）。表结构见 [13-数据模型 §十一](13-数据模型.md#十一多租户)。

### 12.1 两层关系

| 层 | 作用 | 能放宽吗 |
|----|------|----------|
| **租户（`tenant_id`）** | 硬边界：只能看到**当前生效租户**的数据 | ❌ 不能。任何数据档位都在租户之内生效 |
| **数据档位（`sys_role.data_scope`）** | 软范围：租户**内部**按「仅本人 / 本部门 / …」收窄 | ✅ 档位 1（全部数据）= 本租户全部数据，**不是**全库 |

两者**串联（AND）而非替代**：先按租户切一刀，再在租户内按档位收窄。

### 12.2 为什么租户条件必须独立成最外层作用域

`BaseModel::$globalScope = ['tenant', 'dataScope']`（**tenant 在前**）。原因：

- `DataScope::row()` 在**超管**与**档位 1（全部数据）**时**直接 `return`**（不加任何条件）。
  若把租户条件塞进这个函数里，超管与「全部数据」档位就会**绕过租户条件跨租户看到所有数据**。
- 独立作用域后，「超管」「全部数据」放行的只是**数据权限**，租户条件仍然生效。

### 12.3 直查构造器（`Db::name()`）必须走 `TenantContext`

`Db::name()` 绕过一切模型作用域，因此**受控表一律不得直查**（`DataScopeChecker` R2 会报错）。需要直查时统一用
[`support/TenantContext.php`](../../server/plugin/cccms/support/TenantContext.php)：

| 方法 | 用途 |
|------|------|
| `TenantContext::TABLES` / `participates($table)` | 受控表清单 / 判断某表是否参与租户隔离 |
| `TenantContext::table($name)` | 取已叠加租户条件的查询构造器（替代 `Db::name($name)`） |
| `TenantContext::applyToQuery($query, $table)` | 给已有查询补租户条件（含别名场景） |
| `TenantContext::stamp($data, $table)` | 写入前补齐 `tenant_id`（`ScopedQuery` 已统一调用，业务代码无需手写） |

### 12.4 与「逃生口」的联动

- `withoutGlobalScope()` **只跳出数据权限，保留租户**；`withoutAllScopes()` 才跨租户 —— 见 §六。
- 因此历史代码里为「看全量」写的 `withoutGlobalScope()` **不会**变成跨租户口子，但它也**不再**适合做全局唯一键查重。
- 唯一键（`uk_username` / 角色·岗位·租户 `uk_code` / 字典 `uk_type` / 受控表 `uk_table` / 菜单 `uk_node`）
  **均不含 `tenant_id`**，查重必须跨租户。

### 12.5 平台级的管理动作

| 动作 | 权限要求 |
|------|----------|
| 租户列表 / 新增 / 修改 / 删除（`/tenant*`） | `TenantLogic::assertPlatformAdmin()`：**必须是超管，且当前生效租户 = 平台租户**（超管切进某租户后即失去该入口） |
| 切换租户（`/auth/switchTenant`） | `TenantLogic::assertSuperAdmin()`：仅超管；重签带 `tid` 声明的令牌并迁移在线会话 `jti` |
| 租户下拉（`/auth/tenants`） | 登录即可，仅超管返回全部租户，其他账号只返回当前租户 |

> 授权时**不要把** `cccms:tenant*` 节点下发给租户内角色：接口在 `assertPlatformAdmin()` 处会再次拦截。

### 12.5 自定义域名：入口收窄，不改变身份来源

租户可绑定自有域名（`sys_tenant.domain`，唯一索引），由 [`support/TenantDomain.php`](../../server/plugin/cccms/support/TenantDomain.php) 解析请求 Host → 租户。

| 访问方式 | 租户切换器（`/auth/tenants`） | 切换租户（`/auth/switchTenant`） | 登录（`/auth/login`） |
|---|---|---|---|
| **主域名**（未命中任何 `domain`） | 平台条目 + 全部启用租户 | 任意合法租户 | 按账号归属租户登录 |
| **租户自定义域名**（命中租户 D） | **只返回 D**，平台条目不出现 | **只允许 D**；切平台或切其它租户 → `403` | 账号归属必须是 D；平台归属（`0`）的账号须同时是超管，登录后以 D 身份进入，否则 `403` |

几条硬约束：

- **域名只用于收窄入口，不决定身份。** 身份仍由令牌 `tid` + [`AuthService::buildContext()`](../../server/plugin/cccms/support/AuthService.php) 校验；域名命中**不会**自动提权，也不会跳过角色 / 数据权限。
- **归一化统一口径。** `TenantDomain::normalize()` 做小写、去协议、去端口、去尾部点；入库（`TenantLogic::pick()`）与查询（`resolve()`）走同一个函数，避免「存 `CRM.Example.com`、请求来 `crm.example.com`」匹配不上。
- **空值必须是 `NULL`，不能是空串。** 唯一索引允许多行 `NULL`，但只允许一个空串 —— 若把「未绑定」写成 `''`，第二个未绑定租户就会写入失败。
- **生效延迟 60 秒。** 解析结果在进程内缓存，保存租户后由 `TenantDomain::flush()` 立即失效。
- **软删仍占位。** 回收站中的租户依然占用其域名（与 `code` 同口径），唯一性校验会提示「已被回收站占用」。
- **CLI / 定时任务没有域名概念。** `TenantDomain::fromRequest()` 在无请求上下文时返回 `null`，即按主域名口径处理。
