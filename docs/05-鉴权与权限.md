# 鉴权与权限

> 本文讲「谁能调用哪个接口、谁能看到哪个菜单」。包括 4 个注解、鉴权规则矩阵、权限节点规范、RBAC 数据模型与角色继承。数据权限（行 / 字段级）另见 [06-数据权限](06-数据权限.md)。

---

## 一、总览

CCCMS 的鉴权分三层，彼此正交：

| 层 | 解决什么 | 机制 |
|----|----------|------|
| **认证** | 你是谁 | JWT（Bearer token）→ `AuthService::buildContext()` 实时构建 `UserContext` |
| **接口权限** | 你能不能调这个接口 | 控制器方法上的注解 + `CheckAuth` 中间件（按钮级 RBAC） |
| **数据权限** | 你能看到 / 改哪些数据 | 角色 `data_scope` + `sys_data_rule`，模型层自动生效（见 06） |

---

## 二、唯一声明机制：4 个注解

全部是 PHP 8 原生属性（Attribute），位于 `plugin/cccms/support/attribute/`，**一律使用命名参数**。

| 注解 | 可写位置 | 参数 | 语义 |
|------|----------|------|------|
| `Permission` | 方法 | `slug`（必）/ `title`（必）/ `sort` / `group` | 业务接口：**需登录 + 需权限** |
| `NoAuth` | 方法 | `title` | 登录即可，无需按钮权限（如个人资料） |
| `NoLogin` | 类 / 方法 | `title` | 完全匿名（登录页、验证码） |
| `Restrict` | 类 / 方法 | `methods` / `encode` | 追加约束：请求方法白名单 / 响应编码白名单 |

### 2.1 示例

```php
#[Permission(slug: 'cccms:user:index', title: '用户列表')]
#[Restrict(encode: ['json', 'xml'])]
public function index(Request $request): Response { /* ... */ }

#[Permission(slug: 'cccms:user:save', title: '用户保存')]
#[Restrict(methods: ['POST'])]
public function save(Request $request): Response { /* ... */ }

#[NoAuth(title: '修改密码')]
public function password(Request $request): Response { /* ... */ }

#[NoLogin(title: '登录')]
#[Restrict(methods: ['POST'])]
public function login(Request $request): Response { /* ... */ }
```

### 2.2 互斥规则

- `Permission` / `NoAuth` / `NoLogin` 三者**至多出现一个**（方法级）。
- 类级 `#[NoLogin]` 的控制器内**不得**出现 `#[Permission]`。
- 违反互斥会在 `perm-scan` 校验时报错。

### 2.3 `Restrict` 常量

| 常量 | 取值 |
|------|------|
| 方法 | `GET` `POST` `PUT` `DELETE` `PATCH` `HEAD` `OPTIONS` |
| 编码 | `json` `jsonp` `xml` `view` |

`methods = []` 表示不校验方法；`encode = null` 表示使用全局默认（`['json']`）。

## 三、鉴权规则矩阵（fail-closed）

`CheckAuth` 的判定：

| 方法上的属性 | 需登录 | 需权限 | 结果 |
|--------------|--------|--------|------|
| **无任何属性** | — | — | **拒绝**（500 +「接口未声明权限」） |
| `#[Permission]` | ✅ | ✅ 校验 slug | 无权限 → 403 |
| `#[NoAuth]` | ✅ | ❌ | 通过 |
| `#[NoLogin]` | ❌ | ❌ | 通过（且 `CheckLogin` 直接跳过） |
| `#[Restrict]` | 由其它属性决定 | 只追加约束 | 405 / 406 |

> ⚠️ **陷阱**：新增控制器方法忘记写注解 → 接口直接 500。这是**有意的**：漏配的代价是「不可用」（立刻被发现），而不是「无校验」（被越权）。

超管（持有 `super_admin` 角色）在 `CheckAuth` 中直接放行全部 slug。

## 四、权限节点（slug）规范

**权限节点标识 = 显式 slug**，命名约定：

```
{插件}:{模块}:{动作}      // 至少 3 段，全小写
```

- 正则：`^[a-z][a-z0-9_]*(:[a-z][a-z0-9_]*){2,}$`（`PermScanner::SLUG_PATTERN`）
- 第一段固定为插件名，使「权限标识 / 后端控制器 / 前端页面」三者可互相推导。
- 最后一段是动作；其之前的全部段拼起来 = **归属菜单 slug**（由 `PermScanner` 做**最长前缀匹配**）。
- **全局唯一**，由 `perm-scan` 强制校验。

示例：

| slug | 归属菜单 | 控制器 | 前端页面 |
|------|----------|--------|----------|
| `cccms:user:index` | `cccms:user` | `UserController::index` | `pages/cccms/user/index.vue` |
| `cccms:user:reset_password` | `cccms:user` | `UserController::resetPassword` | 同上 |
| `cccms:data_rule:table_index` | `cccms:data_rule` | `DataScopeTableController::index` | `pages/cccms/data_rule/index.vue` |

### 4.1 `group` 参数的用途

当 slug 的模块段与「想挂的菜单」不一致时，用 `group` 显式指定归属菜单。例如回收站的节点挂在「系统设置」菜单下：

```php
#[Permission(slug: 'cccms:recycle:restore', title: '恢复回收站数据', group: 'cccms:setting')]
```

`PermScanner::resolveParent()`：**先看 `group`，没有才用 slug 最长前缀**。

### 4.2 非权限点方法

`NoAuth` / `NoLogin` 不产生权限节点（`slug = null`），但可以给一个 `title`，作为**操作日志里的操作名**（否则日志显示「—」）。例如 `#[NoAuth(title: '修改密码')]`。

### 4.3 注解 `title` 保持中文，多语言在返回时覆盖

`#[Permission(title:)]` 里的中文标题会作为按钮节点的初始 `title` 写入库中，**不要求写多语言**：
`MenuLogic::localizeTitles()` 会在返回菜单树（`/menu/tree` 与 `/menu/userTree`）时，按 `menu.{slug}`
命中语言包才覆盖为当前请求语言，因此节点标题天然多语言；管理员自建菜单没有对应 slug，原样返回。
详见 [08-后端开发规范 §十三](08-后端开发规范.md#十三国际化i18n)。

## 五、认证链路

### 5.1 `CheckLogin`（认证）

1. 方法 / 类带 `#[NoLogin]` → 直接放行。
2. 取 `Authorization: Bearer <token>`（正则 `^Bearer\s+(\S+)$/i`）；无 token → 401。
3. `TokenService::verify()` 校验 JWT。
4. `AuthService::buildContext($userId)` **从数据库实时构建** `UserContext`，挂到 `$request->user`。
5. 构建失败（用户被禁用 / 软删 / 无角色异常）→ 401。

### 5.1.1 权限集合缓存（`PermissionCache`）

`AuthService::buildContext()` 的取数策略是**拆开缓存**：

| 数据 | 策略 | 原因 |
|------|------|------|
| 用户行（状态 / 昵称 / 头像） | **每请求实时查库** | 保证「禁用 / 删除用户立即 401」这条硬约束不被缓存破坏 |
| 角色 + 权限节点集合 | `PermissionCache`（Redis） | 否则每次请求固定 3~4 条 SQL |

- 缓存键为 `cccms:auth:ctx:{版本}:{用户ID}`，版本号是只增不减的 `cccms:auth:ver`。
- 任何 RBAC 变更（角色、授权节点、菜单、用户角色关系、回收站恢复 / 彻底删除、
  菜单同步、权限扫描、清理缓存）都会调用 `PermissionCache::bump()` → 版本 +1 → **旧键立即失效**，
  无需遍历删除，也不怕漏删；旧键靠 300s 兜底 TTL 自然回收。
- Redis 不可用时 `version()` 返回 0，读写全部退化为「不使用缓存」，即回到实时查库行为。

### 5.2 `TokenService`（JWT）

| 方法 | 说明 |
|------|------|
| `issue(int $userId, array $claims = [])` | 返回 `{token, expires_in, expires_at}` |
| `verify(string $token)` | 返回 claims；过期 / 签名错误 / 未生效分别给出不同 401 文案 |

- 算法 HS256；payload 含 `iss`/`sub`/`iat`/`nbf`/`exp`/`jti`。
- 有效期优先取 `security.token_ttl`，回退 `config('plugin.cccms.auth.ttl')`，**默认 2 小时**。
- 密钥取 `config('plugin.cccms.auth.secret')`，为空抛 500；**生产必须用 `JWT_SECRET` 注入**。

**滑动续期**（`TokenService::shouldRenew()` + `CheckLogin::renew()`）：

| 项 | 说明 |
|----|------|
| 触发条件 | 令牌**剩余有效期不足 TTL 的 1/3**（`shouldRenew`，已过期 / 缺 `exp` 一律不续，交给 401） |
| 下发方式 | 响应头 `X-Refresh-Token`（跨域下由 `Cors` 的 `Access-Control-Expose-Headers` 声明可读） |
| 前端 | `api/request.ts` 响应拦截器读到即 `setToken()` **静默替换**，用户无感；导出类 blob 响应也走同一分支 |
| 在线会话 | 续期后 `jti` 变了，`OnlineSession::rotate()` 把会话迁到新 `jti` —— 否则「强制下线」踢的是已废弃的旧令牌 |
| 旧令牌 | **刻意不写入黑名单**：同一页面常并发多个请求，立即拉黑会让在途请求被判 401 而跳登录；旧令牌自然过期即失效 |

> 为什么缩短 TTL：令牌存在 `localStorage`，TTL 就是 XSS 一旦发生攻击者能用的窗口长度；
> 7 天等于长期凭证。缩短后靠续期保证活跃用户不掉线 —— 两者必须成对出现。

### 5.3 登出与会话失效

三层机制，各管一段：

| 机制 | 作用域 | 说明 |
|------|--------|------|
| `TokenBlacklist::revoke($jti, $exp)` | **单令牌** | 登出时把当前 `jti` 写入 Redis 黑名单，TTL = 剩余有效期；`CheckLogin` 每次校验 |
| `TokenBlacklist::revokeUser($userId)` | **单用户全部令牌** | 「强制下线」用：记录该用户的时间分界线，`iat <= cutoff` 的令牌全部作废 |
| `SessionGuard` | **全局** | 全局时间分界线，用于**开启维护模式时踢掉非超管** |

- 三者都在 Redis（跨进程共享）；**Redis 不可用时静默降级为「不拦截」**（失效名单属加固层，
  不应因缓存故障把所有人挡在门外）。
- `isStale` / `isUserStale` 用 `<=` 而非 `<`：包含「与分界线同一秒签发」的令牌，
  否则同秒签发的令牌会成为漏网之鱼；取不到 `iat` 的异常令牌视为失效（fail-closed）。
- 登录成功时会 `TokenBlacklist::clearUser()`：避免与该用户的分界线**同一秒**签发的新令牌被误判。
- 「在线用户」页面（[07-功能模块](07-功能模块.md#十九在线用户online)）按会话 / 按用户下线时，
  会同时调 `OnlineSession::remove*()` 与 `TokenBlacklist` —— 只做前者属于「假下线」。

### 5.4 登录失败限流（`LoginThrottle`）

| 配置 | 说明 |
|------|------|
| `security.login_fail_limit` | 同一账号连续失败达到该次数后锁定；`0` = 关闭 |
| `security.login_fail_window` | 锁定时长（分钟） |
| `security.login_fail_ip_limit` | 同一 IP 的失败次数阈值（默认 20） |

- key：`cccms:login_fail:user:{用户名小写}` 与 `cccms:login_fail:ip:{IP}`，两维度独立计数；`recordFailure()` 首次失败或达阈值时设置 TTL。
- 账号维度达阈值抛 `ApiException(..., 429)`；IP 维度达阈值**只限流该 IP、不锁账号**，避免攻击者用错误密码锁死他人账号。
- IP 取 `ClientIp::resolve()`（可信代理白名单，见 [02-安装部署 §5.4](02-安装部署.md#54-反向代理下的真实-ip-溯源必配)）。
- **fail-open**：Redis 不可用按「不锁定」处理（限流属加固，不应因缓存故障把所有人挡在门外）。

### 5.5 图形验证码（`Captcha`）

- 由 `security.login_captcha` 控制开关；关闭时 `GET /auth/captcha` 返回 `null`。
- SVG 生成，不依赖 GD；字符集去掉了易混的 `0/O/1/I`。
- 答案存 Redis，TTL 300s；**校验后无论对错立即删除**（一次性），比对用 `hash_equals`。

### 5.6 密码策略（`PasswordPolicy`）

- 新增用户 / 重置密码 / 找回密码 / 个人中心改密共用 `PasswordPolicy::assertValid()`。
- 长度取 `security.password_min_length`（默认 6）与 `security.password_max_length`（默认 64，避免超长口令放大 bcrypt 开销），用 `mb_strlen` 判断。
- 字符类别数取 `security.password_strength`（默认 2 类：大写 / 小写 / 数字 / 符号）。
- 内置弱口令黑名单（约 90 条），并拒绝与用户名 / 昵称 / 邮箱相同或包含（身份信息每次校验时实时读取）。
- 密码以 bcrypt 存储。

### 5.7 维护模式

| 环节 | 行为 |
|------|------|
| `Maintenance` 中间件 | 开启 `system.maintenance` 后，非超管调用任何接口 → 503 |
| `CheckLogin` | 维护模式第一次生效时调用 `SessionGuard::cut()`（幂等），非超管旧 token 失效 → 401 |
| `AuthLogic` | 维护模式下**只有超管能登录**，其余明确拒绝 |
| 前端 | 登录页展示维护公告（`GET /config/ui` 公开） |

## 六、RBAC 数据模型

```
用户 sys_user ──┬── sys_user_role ──→ 角色 sys_role ──┬── sys_role_node ──→ 菜单 / 权限节点 sys_menu
                │                                     └── parent_id（角色继承）
                ├── sys_user_dept ──→ 部门 sys_dept ──→ sys_dept_role（部门↔角色）
                └── sys_user_post ──→ 岗位 sys_post
```

| 表 | 作用 |
|----|------|
| `sys_user` | 用户 |
| `sys_role` | 角色（`code` 唯一、`data_scope`、`parent_id` 继承） |
| `sys_user_role` | 用户 ↔ 角色（直连） |
| `sys_menu` | 菜单 + 权限节点树（`type` 1 目录 / 2 菜单 / 3 按钮，`node` = slug 唯一） |
| `sys_role_node` | 角色 ↔ 节点授权（`node` = slug） |
| `sys_dept` / `sys_user_dept` / `sys_dept_role` | 部门 / 用户部门 / 部门角色 |
| `sys_post` / `sys_user_post` | 岗位 / 用户岗位 |
| `sys_tenant` | 租户（多租户硬边界；`id = 0` 为平台租户，虚拟不落库） |

### 6.1 超管的定义

**超管 = 持有 `sys_role.code = 'super_admin'` 的角色**（不是 `id === 1` 硬编码）。

- 该角色禁止编辑 / 删除。
- 绕过接口权限校验与数据权限。
- **不写入权限缓存**（避免缓存把超管"降级"）。
- 种子数据中 `id = 1` 即 `super_admin`。
- ⚠️ **不绕过租户边界**：超管能绕过的只有「接口权限 + 数据权限」，租户条件（`tenant_id`）
  是最外层硬边界，超管同样只能看到**当前生效租户**的数据；跨租户必须**显式切换**
  （`POST /auth/switchTenant`，重签带 `tid` 的令牌）。详见
  [06-数据权限 §十二](06-数据权限.md#十二多租户租户是硬边界档位是租户内的软范围)。

### 6.2 角色继承（方案 A：子角色继承父角色）

- **子角色可用节点 = 自身节点 ∪ 祖先链节点**（沿 `sys_role.parent_id` 向上递归）。
- 新增子角色**不影响父角色**（无隐式扩权）。
- `data_scope`（数据档位）**不继承父角色**：只按直连角色取最宽松（`min`）生效；
  有效角色（直连 + 祖先）只用于「数据权限规则绑定角色」与 `{role.ids}` 取值。
  详见 [06-数据权限](06-数据权限.md#二角色级预置范围sys_roledata_scope)。
- 授权界面中，继承来的节点**只读**展示。
- 保存时强制**环检测 + 深度上限 5**（`AuthService::effectiveRoleIds()` 每步去重防环）。
- 已进回收站的角色不参与继承。

> **复制角色**（`POST /role/copy`，节点 `cccms:role:copy`）只复制角色本体与**自身** `role_node`
> 授权，**不含继承来的祖先节点**（避免源角色调整后副本失效），也不复制子角色。因 `data_scope`
> 不继承，复制时**必须显式复制档位**，否则副本会静默落到默认「仅本人」。父角色做存在性 + 深度 ≤5
> 校验（同时兜住历史脏数据中的环）。

> `AuthService::effectiveRoleIds()` 返回「直连角色 + 所有祖先角色」；`permissions()` 再取这些角色的 `role_node.node` 并集，并剔除「菜单已被软删」的节点（授权行保留在 `sys_role_node` 里，**恢复菜单后自动重新生效**）。

### 6.3 菜单可见性（`/menu/userTree`）

`MenuLogic::userTree(UserContext $user)`：

- 超管 → 全量菜单。
- 普通用户 → 只有命中 `permissions` 的节点，并**向上传播父节点可见性**（父目录即使没有独立权限，只要子节点可见也展示）。

前端据此生成动态路由与侧边栏，见 [09-前端开发规范](09-前端开发规范.md#四路由机制)。

## 七、前端按钮权限：`v-auth`

```vue
<el-button v-auth="'cccms:user:save'" type="primary">新增</el-button>

<!-- 支持数组：命中任一即显示 -->
<el-button v-auth="['cccms:recycle:restore', 'cccms:recycle:delete']">回收站</el-button>

<!-- 多根节点组件（如 el-dropdown-item）改用 v-if，v-auth 在这里挂不上 -->
<el-dropdown-item v-if="hasAuth('cccms:user:batch_delete')" command="delete">批量删除</el-dropdown-item>
```

- 指令实现见 `frontend/src/directives/index.ts`：不通过时用 `display: none` 隐藏（不移除 DOM）。
- 判断依据是 `userStore.hasAuth()`：超管直接通过，否则比对 `permissions`（数组命中任一）。
- `permissions` 来自登录后 `GET /auth/me` 返回的用户信息。
- **只能挂在「根节点是单个元素」的组件上**（`el-button` / `el-dropdown` / `el-upload` 等）。
  多根节点组件（典型是 `el-dropdown-item`，内部是 `ElRovingFocusItem`）挂不上，Vue 会打印
  `Runtime directive used on component with non-element root node` 告警且**权限隐藏静默失效**。
  这类场景在页面里从 `useUserStore()` 取 `hasAuth`，用 `v-if="hasAuth('...')"` 条件渲染。

> ⚠️ **注意**：`v-auth` 只是**界面显隐**，真正的拦截在后端 `CheckAuth`。两者必须同时配置，不能只做前端。

### 7.1 路由级守卫（节点校验）

按钮级之外，页面级也要拦一道：`frontend/src/router/index.ts` 的 `beforeEach` 在完成
「静态路由 → 动态路由（菜单驱动）→ 按 path 重新导航」之后，会校验目标路由的 `meta.node`：

```ts
const node = to.meta.node
if (typeof node === 'string' && node && !user.hasAuth(node)) {
  return { path: '/403', replace: true }
}
```

- `meta.node` 由菜单驱动动态注册时写入（值即该菜单的权限节点）。
- 无权限 → 重定向到 `/403`（`pages/cccms/error/403.vue`，**刻意不声明 `meta.node`**，否则会自锁死循环）。
- 判据同样是 `userStore.hasAuth()`：超管直通。
- 手输 URL / 收藏夹直达某个无权限页面时，靠这一层兜住；后端 `CheckAuth` 仍是最终防线。

## 八、权限节点的生成与同步

```
控制器注解 ──perm-scan──→ sys_menu(type=3 按钮)
db/menu.php ──menu-sync──→ sys_menu(type=1/2 目录与菜单)
```

### 8.1 `perm-scan` 的校验（`PermScanner::validate`）

1. 接口必须声明注解（fail-closed）。
2. 类级 `NoLogin` 内不得有 `Permission`。
3. slug 格式合法。
4. slug 全局唯一。
5. `Restrict` 的 methods / encode 取值合法。

任一不通过 → 命令退出码 1（可接 CI）。

### 8.2 `perm-scan` 的同步策略

- **只增不删**：已存在的节点仅做「恢复软删」+「纠正归属父节点」，**不覆盖管理员改过的 title / sort**。
- 找不到归属菜单 → 抛 500（说明 `db/menu.php` 里缺对应的菜单节点）。
- `zombieNodes()` 报告「代码里已无对应注解」的按钮节点（回收站里的不算僵尸）。

> ⚠️ **陷阱**：`PermScanner::sync()` 与 `MenuSyncer::syncNode()` 查询已存在节点时必须 `Menu::withTrashed()`，否则永远查不到回收站里的节点，「恢复」形同虚设。

## 九、新增一个「需要权限的接口」

以「导出操作日志」为例（现有实现，见 `LogController::export()`）：

**后端**

1. 在 `LogController` 增加方法并声明注解：

   ```php
   #[Permission(slug: 'cccms:log:export', title: '导出操作日志')]
   public function export(Request $request): Response
   {
       return LogLogic::export($request->get());
   }
   ```

2. 在 `config/route.php` 注册路由：

   ```php
   Route::get('/log/export', [LogController::class, 'export']);
   ```

3. 执行 `php webman cccms:perm-scan`，按钮节点自动挂到「日志管理」（`cccms:log`）菜单下。

4. 在「权限配置 → 角色管理」把该节点授予相应角色。

**前端**

5. 加接口封装与按钮：`v-auth="'cccms:log:export'"`。

**自检**

6. `php webman cccms:perm-scan --check`（只校验不写库）应通过。
