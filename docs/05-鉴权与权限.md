# 鉴权与权限

> 从「谁能登录」到「能点哪个按钮」：令牌、会话、租户、RBAC 与前端指令的完整链路。

---

## 一、登录流程

```text
GET  /api/auth/login-context   取站点信息、租户列表、验证码开关
GET  /api/auth/captcha         需要时下发图形验证码
POST /api/auth/login           校验租户 + 账号 + 口令 + 验证码
      → 签发 JWT
      → 写入在线会话（Redis）
      → 记录登录日志
      → 返回用户资料、权限、菜单
```

### 1.1 租户识别顺序

1. 请求 `Host` 命中 `sys_tenant.domain` → 锁定该租户，登录页不允许切换。
2. 未绑定域名 → 登录页展示可选租户，用户手动选择。
3. 未选择 → 使用 `CCCMS_LOGIN_DEFAULT_TENANT`（默认 `platform`）。

> ⚠️ **注意**：域名锁定的租户与令牌中的 `tid` 不一致时，请求会以「当前域名与登录租户不匹配」拒绝。跨租户运营必须使用平台租户的超管并通过「切换租户」重新签发令牌。

### 1.2 登录校验

| 校验 | 失败提示 |
|------|----------|
| 租户存在且启用 | 租户不存在或已停用 |
| 用户名存在、未软删 | 账号或密码错误（统一文案，避免枚举） |
| 口令 Argon2 校验 | 账号或密码错误 |
| 用户状态启用 | 账号已停用 |
| 租户到期时间 | 租户已到期 |
| 图形验证码（按配置开启） | 验证码错误或已过期 |
| 登录失败限流 | 尝试过于频繁，请稍后再试 |

验证码开关是业务配置 `security.login_captcha`，按租户读取；登录页与 `/auth/captcha` 使用同一租户上下文，避免出现「页面不显示验证码但登录要求验证码」。

登录失败计数按 `租户 + 用户名` 分桶（同一 IP 另有全局桶），租户 A 的失败不会锁死租户 B 的同名账号。连续失败 5 次锁定 15 分钟，单 IP 20 次触发 IP 级限流。

## 二、令牌

### 2.1 结构

HS256 JWT，载荷固定字段：

| 字段 | 含义 |
|------|------|
| `iss` | 固定 `cccms` |
| `sub` | 用户 ID |
| `tid` | 当前租户 ID |
| `hid` | 归属租户 ID（登录时的租户） |
| `iat` / `nbf` / `exp` | 签发、生效、过期时间 |
| `jti` | 令牌唯一 ID，用于吊销与在线会话 |

默认有效期 `CCCMS_TOKEN_TTL=7200` 秒。

### 2.2 双通道

| 通道 | 使用场景 | CSRF |
|------|----------|------|
| `Authorization: Bearer <token>` | SPA 默认 | 不需要（浏览器不会自动携带） |
| HttpOnly Cookie `cccms_token` | 同域部署兼容 | 写请求必须带 `X-CSRF-Token` |

CSRF 令牌存放在非 HttpOnly 的 `cccms_csrf` Cookie 中，中间件用常量时间比较校验；登录、找回密码等匿名 POST 豁免。

> ⚠️ **现状**：本项目前端**只用 Bearer**，没有实现"读 `cccms_csrf` 写 `X-CSRF-Token`"。Cookie 通道是给同域第三方/脚本预留的，要启用必须先在前端补这一段，否则 Cookie 会话的写请求一律 403。

### 2.3 静默续期

当剩余有效期小于 `token_ttl / 3` 时：

1. 生成新 `jti` 与新令牌。
2. 旧 `jti` 的在线会话迁移到新 `jti`。
3. 响应头返回 `X-Refresh-Token`，前端替换本地令牌。

> **提示**：续期不会延长「绝对会话寿命」，每次续期都是完整 TTL；如需强制重新登录，可吊销用户全部令牌。

### 2.4 吊销

三种粒度：

| 粒度 | 触发 | 实现 |
|------|------|------|
| 单令牌 | 退出登录、踢下线、注销我的设备 | Redis 记录 `jti` 黑名单直到 `exp` |
| 用户全部令牌 | 管理员重置密码、用户修改密码、找回密码成功 | `password_changed_at` 作为签发时间水位 |
| 会话清理 | 用户被停用/删除 | 用户上下文加载失败，令牌自然失效 |

## 三、访问策略声明

每个路由必须且只能声明一种：

```python
@permission("cccms:user:save", "新增用户", methods=["POST"])
@no_auth("个人资料")      # 需要登录，但不校验权限节点
@no_login("登录")         # 完全公开
```

| 声明 | 需要登录 | 校验权限节点 | 典型用途 |
|------|----------|--------------|----------|
| `@permission(slug, title)` | 是 | 是 | 业务接口 |
| `@no_auth(title)` | 是 | 否 | 个人中心、工作台、我的消息、导出任务 |
| `@no_login(title)` | 否 | 否 | 登录、验证码、登录上下文、探针 |

`GuardedRoute` 在启动时检查：

- 未声明 → `RuntimeError`，应用无法启动。
- 同时声明多种 → `RuntimeError`。
- `methods` 非空时，请求方法不在列表内 → 405。

> ⚠️ **陷阱**：`@no_auth` 不是「公开接口」。公开接口用 `@no_login`。命名容易误解，新增接口时先确认是否需要登录。

### 3.1 权限节点命名

```text
cccms:<模块>:<动作>
```

示例：`cccms:user:index`、`cccms:role:update`、`cccms:file:upload`。

节点在 `seed` 时写入 `sys_menu`（按钮类型），并通过 `sys_role_node` 授权给角色。菜单树与按钮节点同表，便于前端一次下发。

## 四、RBAC

### 4.1 关系

```text
用户 ──< 用户角色 >── 角色 ──< 角色节点 >── 权限节点
  │                    │
  └──< 用户部门 >── 部门 └── parent_id 角色继承
  └──< 用户岗位 >── 岗位
```

### 4.2 角色继承

- 从用户**直接角色**出发，沿 `parent_id` 向上收集，最多 `MAX_ROLE_DEPTH=5` 层。
- 只收集启用且未删除的角色。
- 权限取所有有效角色的并集。
- 父角色被停用后，继承链在该处断开。

> **提示**：继承只向上，不向下。给「父角色」授权不会自动影响其子角色，只影响直接或间接拥有该父角色的用户。

### 4.3 超级管理员

- 角色编码固定为 `super_admin`。
- 只有**直接拥有**该角色才判定为超管，继承不算。
- 超管跳过权限节点校验与数据范围限制。
- 系统禁止创建或复制编码为 `super_admin` 的角色；删除、停用、回收站还原/彻底删除也有额外保护。
- 只有超管可以给用户授予 `super_admin` 角色；非超管提交的角色 ID 会被过滤。
- 非超管不能修改、重置密码或停用超管账号（批量操作会跳过并计入 `skipped`）。
- 菜单维护要求「超管 + 平台租户」双重条件。
- 角色授权遵循**最小委派**：非超管只能授出自己已拥有的节点，且 `data_scope` 不得比自身更宽。

### 4.4 数据范围

角色上的 `data_scope` 决定行级可见范围（`1` 全部 → `5` 自定义，**数字越大范围越小**）；多角色取**最严**档位（`merge_data_scope` 取 max），任一角色的宽范围不得放大整个账号。档位语义、编译规则与受控表见 [06-数据权限](06-数据权限.md)。

### 4.5 字段解密

字段级规则中的「加密」动作只对以下主体下发前端解密密钥：

- 超级管理员
- 拥有 `cccms:data_rule:save` 或 `cccms:data_rule:update` 的角色

只读审计角色可以看到脱敏值，但拿不到密钥。

## 六、限流与维护模式

### 7.1 限流

- 登录失败按「租户 + 用户名 + IP」计数。
- 已登录接口按用户与路径限流，重接口（导出、生成器、上传等）使用更低阈值。
- Redis 不可用时降级为放行，并在启动时告警。

### 7.2 维护模式

业务配置 `system.maintenance=1` 时：

- 非超管请求在 `load_user()` 阶段被拒绝，返回 `system.maintenance_notice` 文案。
- 超管不受影响，便于处理故障。

## 七、前端权限

### 8.1 路由

- 登录后拉取菜单树，按 `type=2` 且带 `component` 的节点注册动态路由。
- 路由 `meta.node` 写入权限节点，守卫在进入前用 `hasAuth(node)` 再校验一次。
- 超管在前端同样直通。

### 8.2 按钮

```vue
<el-button v-auth="'cccms:user:save'">新增</el-button>
```

`v-auth` 只控制显隐，不构成安全边界；后端 `permission_dependency` 才是最终拦截。

### 8.3 菜单与按钮同步

新增路由并执行 `seed` 后，「菜单管理 → 同步按钮节点」可把新节点写入菜单表；前端「刷新菜单」会重新拉取菜单与权限，无需退出登录。

## 八、常见问题

| 现象 | 原因 | 处理 |
|------|------|------|
| 登录后立刻 401 | 用户无任何启用角色 | 分配至少一个角色 |
| 切换租户后 403 | 非超管尝试跨租户 | 仅超管可切换 |
| 刷新页面 404 | 动态路由未注册完成 | 确认菜单 `component` 路径存在 |
| 按钮不显示 | 角色没有对应节点 | 角色授权后刷新菜单 |
| 接口 405 | `@permission(methods=...)` 未包含实际方法 | 补方法或改调用方式 |
| 一直提示验证码错误 | 租户配置不一致或 Redis 过期 | 检查 `security.login_captcha` 与 Redis |
