# 框架介绍

> 本文讲后端「框架是怎么搭起来的」：插件化架构、请求生命周期、分层约定、统一响应、模型基类，以及长驻内存下的设计纪律。读完应能定位任何一段后端逻辑。

---

## 一、为什么是 Webman

Webman 基于 Workerman，PHP 以**常驻内存**方式运行：框架启动、路由、配置只加载一次，请求不再重新引导。相比传统 PHP-FPM 有三个直接后果，也决定了 CCCMS 的很多设计：

| 后果 | CCCMS 的应对 |
|------|--------------|
| 静态变量会跨请求存活 | 见 [§七、长驻内存的纪律](#七长驻内存的纪律) |
| 权限/配置缓存必须显式失效 | 用 Redis（跨进程）+ `flush()`；数据权限用请求级 `WeakMap` |
| 需要自定义进程做调度 | 定时任务用独立调度进程，每秒 tick |

## 二、插件化架构

Webman 的 `plugin/{name}` 是一个**自包含的应用单元**：拥有自己的 `app/`（控制器、模型、逻辑、中间件）、`config/`（路由、中间件、异常）、`db/`（表结构与菜单声明）。框架在启动时自动发现并加载。

### 2.1 两个内置插件

| 插件 | 定位 | 中间件 | 路由 |
|------|------|--------|------|
| `plugin/cccms` | 后台框架与基础功能 | `Cors → Xss → CheckLogin → RateLimit → Maintenance → CheckAuth → ResponseEncode → OperationLog` | 根路径（`/user`、`/role` …） |
| `plugin/index` | 前台公开应用骨架 | 仅 `Cors` | `/site/*` |

关键点：**中间件按插件作用域生效**。`plugin/index` 没有挂 `CheckLogin` / `CheckAuth`，因此它的路由天然公开，无需 `#[NoLogin]`。这演示了「用插件隔离前台与后台」的标准做法。

> **新建业务插件**：`php webman cccms:plugin-create {name}` 一条命令生成骨架并自动登记菜单，
> 交互式选择**前台**（公开，形态参考 `plugin/index`）或**后台**（需鉴权，形态参考 `plugin/cccms`）。
> 详见 [11-常用命令与运维 §1.13](11-常用命令与运维.md#113-cccmsplugin-create--生成业务插件骨架并登记菜单)。

### 2.2 业务插件的纳管口径

框架通过「**该插件是否提供 `plugin/{插件}/db/menu.php`**」判定它是否是一个 CCCMS 业务插件，并据此把它纳入：

- 菜单同步（`MenuSyncer::menuFiles()`）
- 权限注解扫描（`PermScanner::pluginScanners()`）
- 数据权限接入检查（`DataScopeChecker`）
- 回收站类型扩展（`plugin/{插件}/db/recycle.php`）
- 建表脚本执行（`SqlFileRunner`，跳过 `cccms` 自身）

> 因此 `plugin/index`（无 `db/menu.php`）不会参与权限校验 —— 这正是公开前台应用想要的效果。

### 2.3 插件配置合并

插件配置写在 `plugin/{插件}/config/*.php`，Webman 按插件名合并为 `config('plugin.{插件}.{文件}.{键}')`。例如：

```php
config('plugin.cccms.auth.secret');       // plugin/cccms/config/auth.php
config('plugin.cccms.filesystem.url_prefix');
config('plugin.cccms.response.default');  // ['json']
```

## 三、请求生命周期

```
HTTP 请求
  │
  ├─ Cors               跨域（CORS_ORIGIN 白名单，默认仅同源）；生成 traceId 并接收前端 X-Action-Id / X-Session-Id；OPTIONS 直接 204 返回
  ├─ Xss                递归清洗 POST 字符串（password/content 等豁免）
  ├─ CheckLogin         解析 Bearer token → 校验失效名单 → AuthService 构建 $request->user；
  │                     挂 $request->jti、刷新在线会话活跃时间；#[NoLogin] 跳过
  ├─ RateLimit          按「用户 + 路由」限流（依赖 $request->user，必须在 CheckLogin 之后）；
  │                     超限 429 + Retry-After；未登录跳过；Redis 不可用 fail-open
  ├─ Maintenance        维护模式下仅超管可调用（依赖 $request->user，必须在 CheckLogin 之后）
  ├─ CheckAuth          ① 认证 401 → ② 授权 403 → ③ 未声明权限 500
  ├─ ResponseEncode     ④ 方法白名单 405 → ⑤ 编码白名单 406，确定本次响应编码
  │
  ├─ Controller         薄：解析请求 → 调 Logic → $this->ok(...)
  │    └─ Logic         业务逻辑（数据访问收口）
  │         └─ Model    think-orm；数据权限全局作用域自动注入
  │
  ├─ OperationLog       写操作 / 已登录用户的失败请求落 sys_log（含 trace/action/session；失败不影响业务）
  │
  └─ Result             按编码渲染 json / jsonp / xml / view；失败时附带三个 ID
```

> **三层 ID**：`trace_id`（一次请求，后端生成）+ `action_id`（一次操作，前端生成）
> + `session_id`（一次页面会话，刷新即换，前端生成）。排障看 `/log?action_id=xxx`
> （`GET /log/action`），审计看 `/log?session_id=xxx`（`GET /log/session`），
> 单请求看 `/log/trace?trace_id=xxx`。详见
> [07-功能模块 §十三](07-功能模块.md#十三操作日志log)。

### 3.1 为什么顺序是 401 → 403 → 405 → 406

这是刻意的：**先判身份，再判权限，最后才暴露接口的形状约束**。越权者无法通过「返回 405 还是 406」来推断某个接口是否支持某个方法或编码，从而探测接口结构。

### 3.2 中间件职责速查

| 中间件 | 文件 | 职责 | 关键细节 |
|--------|------|------|----------|
| `Cors` | `plugin/cccms/app/middleware/Cors.php` | 跨域 + **请求标识** | 来源取 `CORS_ORIGIN` 白名单（默认空 = 仅同源）；命中回显具体 Origin + `Vary: Origin`，未命中不下发 CORS 头；生成 `traceId`（回写 `X-Trace-Id`），并校验前端 `X-Action-Id` / `X-Session-Id`（≤32 字节，非法留空） |
| `Xss` | `Xss.php` | POST 入参清洗 | 只改 POST；豁免 password / content 等；移除危险标签与 `on*` 事件 |
| `CheckLogin` | `CheckLogin.php` | 认证 | 无 token / 构建失败 → 401；`#[NoLogin]` 跳过；维护模式踢下线用 `SessionGuard` |
| `RateLimit` | `RateLimit.php` | 接口限流 | 按「用户 + 路由」计数，超限 429 + `Retry-After`；重接口（export/import/generate）单独收紧；未登录不限流；Redis 不可用 fail-open |
| `Maintenance` | `Maintenance.php` | 维护模式 | 非超管 503；未登录放行（登录由 `AuthLogic` 拒绝） |
| `CheckAuth` | `CheckAuth.php` | 授权 | **fail-closed**：无任何注解 → 500 |
| `ResponseEncode` | `ResponseEncode.php` | 方法 / 编码约束 | 405 / 406，并写入 `$request->encode` |
| `OperationLog` | `OperationLog.php` | 操作日志 | 写操作必记；读操作由 `log.record_read` 控制；递归脱敏 |

## 四、分层约定

```
Controller  →  Logic  →  Model
   薄           厚         薄
```

| 层 | 职责 | 禁止 |
|----|------|------|
| **Controller** | 解析请求参数、调用 Logic、返回 `ok()` / `fail()`；声明权限注解 | 不写业务逻辑；**不直连数据库**（`DataScopeChecker` R1 会报错） |
| **Logic** | 业务规则、校验、事务、编排；数据访问收口 | 不感知 HTTP（不读 `Request`） |
| **Model** | 表结构映射、数据权限声明、软删除、时间戳 | 不写业务分支 |

- 控制器继承 `plugin\cccms\basic\BaseController`，提供 `ok($data, $message)` / `fail($message, $code, $data)`。
- Logic 为 `final class`，方法多为 `static`，直接返回数组给控制器。
- 异常统一抛 `ApiException($message, $code)`，由 `ExceptionHandler` 渲染。

## 五、统一响应 `Result`

统一信封：

```json
{ "code": 0, "message": "ok", "data": { } }
```

| 方法 | 说明 |
|------|------|
| `Result::ok($data = null, $message = 'ok')` | 成功，`code = 0`，HTTP 200 |
| `Result::fail($message, $code = 1, $data = null)` | 失败；HTTP 状态码仅在 `code` 落在 400–599 时等于 `code`，否则为 200 |
| 编码 | 由 `ResponseEncode` 中间件决定，请求侧用 `?format=xxx` 选择 |

| 编码 | 说明 |
|------|------|
| `json`（默认） | 标准 JSON |
| `jsonp` | 回调名经正则白名单过滤，非法回落为 `callback` |
| `xml` | 数组转 XML，键名与值均转义；整型键映射为 `item` |
| `view` | 从 payload 取 `template` / `vars` 渲染模板 |

编码允许集 = 方法上 `#[Restrict(encode: [...])]` 的声明，缺省取 `config('plugin.cccms.response.default')`，即 `['json']`。请求的 `format` 不在允许集 → **406**。

> ⚠️ **陷阱**：`Result::fail('x', 1)` 的 HTTP 状态码是 **200**（因为 1 不在 400–599）。前端判断成功与否**只看 `code === 0`**，不要看 HTTP 状态码。

### 5.1 约定俗成的错误码

| code | 语义 |
|------|------|
| 401 | 未登录 / 凭证失效 |
| 403 | 权限不足 / 越权访问 |
| 405 | 请求方法不允许 |
| 406 | 响应编码不允许 |
| 422 | 参数 / 校验失败 |
| 429 | 触发限流（登录失败锁定） |
| 500 | 服务端错误（含「接口未声明权限」） |
| 503 | 维护中 |

## 六、异常处理

`plugin/cccms/support/ExceptionHandler.php` 实现 Webman 的异常处理器：

- `report()`：`Log::error((string)$exception)`。
- `render()`：
  - `ApiException` → `Result::fail($message, $code, $data)`；
  - 其它异常 → debug 开启时透出 `getMessage()`，否则统一返回「服务器内部错误」+ 500。

业务代码只需：

```php
throw new ApiException('无权操作该用户', 403);
```

此外，全局路由 404 兜底（`server/config/route.php`）会返回统一 JSON，并把「方法 + 路径 + referer + ua」追加到 `runtime/logs/route-404.log`，便于排查「前端调了不存在的接口」。

## 七、长驻内存的纪律

这是使用 CCCMS 最容易踩坑的地方，务必牢记。

| 场景 | 正确做法 | 错误做法 |
|------|----------|----------|
| 取当前用户 | `request()->user`（`UserContext`，随请求销毁） | 自建静态容器 / `Fiber` 非 fiber 上下文（会跨请求泄漏身份） |
| 系统配置 | `SysConfig`（Redis → MySQL，保存后 `flush()`） | 进程内静态缓存（改配置不生效） |
| 数据权限解析结果 | `DataScope` 内部的 `WeakMap`（键为 `UserContext` 实例） | 静态数组按 userId 缓存（跨请求存活，权限变更不生效） |
| 角色 / 权限集合 | `PermissionCache`（Redis + 全局版本号，RBAC 变更即 `bump()`） | 进程内静态缓存（改权限不生效） |
| 注解元数据 | `PermissionMeta` 的进程内静态缓存（反射结果不随请求变化） | 每次反射（浪费性能） |
| 在线会话 / 令牌黑名单 | Redis（跨进程共享） | 进程内数组（多 worker 不一致） |
| 模型静态属性 | 不存放请求相关数据 | 存放请求相关数据 |

> 判断标准：**「这份数据会不会因为重启前的一次请求而变得不正确？」** 会，就不要放进程内静态缓存。

## 八、模型基类 `BaseModel`

`plugin/cccms/app/model/BaseModel.php` 是所有业务模型的基类，统一了四件事：

### 8.1 表名与时间戳

- 表名统一省略 `sys_` 前缀（连接配置 `prefix = 'sys_'` 自动补全），模型里写 `protected $name = 'user';`。
- `$autoWriteTimestamp = 'datetime'`，`create_time` / `update_time` 由数据库默认值写入。
- 没有 `delete_time` 的模型必须声明 `protected $deleteTime = false;`，否则会拼出不存在的列。

### 8.2 软删除

`BaseModel` 使用 think-orm 的 `SoftDelete` trait：

| 场景 | 用法 |
|------|------|
| 普通查询 | 自动排除已删行 |
| 回收站列表 | `Model::onlyTrashed()` |
| 操作已删行（恢复 / 彻底删除 / 复用回收站节点） | **必须** `Model::withTrashed()` |
| 软删 / 恢复 | `Model::destroy($ids)` / `$model->restore()` |

> ⚠️ **陷阱**：模型默认条件是 `delete_time IS NULL`，若不加 `withTrashed()` 去「操作已删行」，UPDATE 会**静默变成 0 行**，表现为「同步了但没生效」。

### 8.3 数据权限全局作用域

```php
protected $globalScope = ['tenant', 'dataScope'];  // 租户（硬边界）在前，档位在后
protected $dataScope    = [];                      // false = 不参与；数组 = 覆盖 owner/dept/no_baseline
public static function newScopedQuery();           // 返回带作用域的查询
```

只要查询走模型，列表、详情、`count()`、按 id 直调的编辑 / 删除都被自动覆盖。业务层不需要（也不应该）再手写范围判定。详见 [06-数据权限](06-数据权限.md)。

### 8.4 出参 / 入参字段级规则

- **出参**：`toArray()` 统一应用 `hidden` / `mask` / `encrypt`。
- **入参**：`$query = ScopedQuery::class`，在写入前剔除不可写字段（四种字段级动作全部剔除）。

## 十、fail-closed 与 fail-open 的取舍

框架对不同层采用不同默认：

| 层 | 策略 | 示例 |
|----|------|------|
| **安全边界** | fail-closed（拒绝） | `CheckAuth` 未声明注解 → 500；数据权限无规则 / 无部门 → 看不到数据 |
| **加固 / 体验层** | fail-open（放行 + 降级） | `LoginThrottle` Redis 挂了 → 不锁定；`SessionGuard` Redis 挂了 → 不限制；`SysConfig` 异常 → 返回默认值 |

判断方法：**「失败时放行会不会导致越权？」** 会，就 fail-closed；不会，就 fail-open，避免因基础设施抖动把业务整体打挂。
