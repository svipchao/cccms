# 后端开发规范

> 目标：新增一个模块时不用猜「文件放哪、参数怎么校验、事务谁来提交、权限怎么声明」。

---

## 一、新增模块的完整步骤

以 `demo` 模块为例：

1. **模型** `models/demo.py`
   - 继承 `BaseModel`、`TenantMixin`，按需加 `SoftDeleteMixin`。
   - 唯一约束把 `active_flag` 放进组合键。
   - 外键写明 `ondelete`。

2. **Schema** `schemas/demo.py`
   - 入参继承 `StrictModel`，出参继承 `StrictModel` 或 `ORMModel`。
   - 时间字段用 `LocalDateTime` / `OptionalLocalDateTime`。
   - 查询参数单独建 `DemoQuery`。

3. **服务** `services/demo.py`
   - 函数签名：`async def list_demos(session, actor, params)`。
   - 查询前 `apply_scope(select(Demo), Demo)`。
   - 写操作在服务内 `commit()`。
   - 返回 Pydantic 出参，不返回 ORM 对象给路由。

4. **路由** `api/demo.py`
   - `router = make_router(prefix="/demo", tags=["demo"])`。
   - 每个端点必须声明 `@permission(...)` / `@no_auth(...)` / `@no_login(...)`。
   - 返回 `ok(data)`。

5. **注册** `api/__init__.py`
   - 加入 `BUSINESS_ROUTERS`，自动挂到 `/api`。

6. **权限节点**
   - 执行 `python -m cccms.cli seed`，把新节点写入菜单表。
   - 到「角色管理」给角色授权。

7. **验证**
   - `python -m cccms.cli check`（路由声明）
   - `ruff check src`
   - `mypy src`
   - 手工验证列表、详情、创建、更新、删除、回收站、越权访问。

## 二、路由层规范

```python
router = make_router(prefix="/demo", tags=["demo"])


@router.get("", response_model=ApiResponse[PageResult[DemoOut]])
@permission("cccms:demo:index", "示例列表")
async def index(
    keyword: str | None = None,
    page: int = 1,
    limit: int = 15,
    user: UserContext = Depends(get_current_user),
    session: AsyncSession = Depends(get_session),
) -> dict[str, object]:
    total, rows = await demo_service.list_demos(session, user, DemoQuery(keyword=keyword, page=page, limit=limit))
    return ok(PageResult(total=total, list=rows))
```

规则：

- 一个业务域一个文件，前缀与文件名一致。
- 路由函数不写 SQL、不 `commit()`、不拼响应信封。
- 需要当前用户时用 `Depends(get_current_user)`，不要从 `current_context()` 直接取（便于类型检查）。
- 列表参数用显式 `Query` 参数，复杂查询再建 `Query` 模型。
- 文件上传用 `UploadFile`，注意字段别名与前端 `FormData` 一致。

### 2.1 三种访问声明

| 声明 | 用途 |
|------|------|
| `@permission(slug, title, methods=[...])` | 需要登录 + 权限节点 |
| `@no_auth(title)` | 需要登录，不校验节点 |
| `@no_login(title)` | 公开 |

写操作建议显式给 `methods=["POST"]`，让方法不匹配时返回 405 而不是落到路由函数。

## 三、服务层规范

### 3.1 事务

- 一个业务动作一次 `commit()`。
- 循环内批量操作时，可用 `begin_nested()` 做单条失败隔离，但最终统一提交。
- 捕获 `IntegrityError` 时转换为 `Conflict`，不要把数据库错误抛给前端。

### 3.2 查询

- 列表查询必须 `apply_scope()`。
- 详情/写操作前的可见性校验也必须 `apply_scope()`，不能只按 `id + tenant_id`。
- 分页统一 `offset((page-1)*limit).limit(limit)`，排序字段走白名单。
- 计数用 `select(func.count()).select_from(statement.subquery())`，避免重复写 where。

### 3.3 校验

| 场景 | 异常 |
|------|------|
| 参数格式/业务规则 | `ValidationFailed` |
| 唯一键冲突 | `Conflict` |
| 不存在或不可见 | `NotFound` |
| 越权/租户不匹配 | `Forbidden` |
| 外部依赖不可用 | `ServiceUnavailable` |

> ⚠️ **注意**：不要用 `assert` 做业务校验，生产环境 `-O` 会移除断言。

**错误码与文案**：HTTP 状态码表达协议语义，响应体里的 `code` 表达业务语义，两者已解耦。
新增异常时从 `core/codes.py` 取 `BizCode`，需要多语言时同时给 `message_key`
（键写入 `src/cccms/lang/<locale>/error.json`）：

```python
raise Unauthorized("用户名或密码错误", code=BizCode.LOGIN_FAILED, message_key="error.login_failed")
```

前端只判断 `code === 0` 成功，其余按 `code` 分支；网关/监控看 HTTP 状态码。
禁止在业务代码里写裸数字 `code`，也不要再让 `code` 等于 HTTP 状态码。

### 3.4 跨租户写入

任何接受外部 ID 的关联写入（角色、部门、岗位、字典类型、父分类）都必须校验目标属于当前租户且未删除。

## 四、模型规范

```python
class Demo(BaseModel, TenantMixin, SoftDeleteMixin, ActiveFlagMixin):
    __tablename__ = "sys_demo"
    __table_args__ = (
        UniqueConstraint("tenant_id", "code", "active_flag", name="uq_demo_code"),
        Index("ix_demo_tenant_status", "tenant_id", "status"),
    )

    code: Mapped[str] = mapped_column(String(64), nullable=False, comment="编码")
```

规则：

- 所有业务表带 `tenant_id`。
- 需要软删除的表继承 `SoftDeleteMixin`；唯一约束包含 `active_flag`。
- 字段写 `comment`，代码生成器与数据规则字段下拉会用到。
- 外键明确 `ondelete`：主数据 `RESTRICT`，可选引用 `SET NULL`，从属数据 `CASCADE`。
- 金额/比例用 `Numeric`，不要用 `Float`。
- 状态用 `SmallInteger`，`1` 启用、`0` 停用。

## 五、Schema 规范

- 入参继承 `StrictModel`（`extra="ignore"`）：前端多传的只读字段会被忽略，不会 422。
- 出参显式列出字段，禁止直接返回 ORM 对象。
- 不要在任何 Schema 中暴露 `password_hash`、密钥、密文。
- 时间字段用 `LocalDateTime`，保证 JSON 输出为 `YYYY-MM-DD HH:MM:SS`。
- 列表出参用 `PageResult[T]`。

```python
class DemoOut(StrictModel):
    id: int
    code: str
    status: int = Field(ge=0, le=1)
    create_time: LocalDateTime
```

## 六、异步规范

- 所有数据库、Redis、文件 IO 使用 `await`。
- 阻塞型操作（git、压缩、大文件哈希）用 `asyncio.to_thread()`。
- 不要在请求内启动 `asyncio.create_task()` 做必须完成的工作，进程重启会丢。
- 后台常驻任务放 `scheduler.py` 或定时任务表。

---

## 七、日志与审计

- 业务日志用 `logging.getLogger("cccms.xxx")`。
- 不要记录明文密码、令牌、验证码、密钥；`core/redact.py` 只兜底常见字段。
- 操作日志由中间件自动记录，无需手写；需要额外业务事件时写 `sys_log` 或专用表。
- 慢请求阈值 `CCCMS_SLOW_LOG_THRESHOLD_MS`。

---

## 八、安全约定

| 风险 | 约定 |
|------|------|
| SQL 注入 | 只用 SQLAlchemy 表达式；动态字段名必须正则校验 |
| 越权 | 写操作前做 `apply_scope()` 可见性校验 |
| 跨租户 | 关联 ID 必须校验租户归属 |
| 文件 | 扩展名白名单 + 服务端推导 MIME + 路径规范化 |
| 导出 | 文件写在 `shared/exports`，只能经鉴权接口下载 |
| 密钥 | 生产启动校验，不入库、不回显 |
| 口令 | Argon2id + 复杂度 + 弱口令字典 |

## 九、提交前检查

```bash
cd backend
uv run python -m cccms.cli check
uv run ruff check src
uv run ruff format --check src
uv run mypy src
uv run pytest
```

| 检查 | 作用 |
|------|------|
| `cli check` | 路由是否都有权限声明 |
| `ruff check` | 未使用导入、复杂度、安全规则 |
| `mypy` | 类型一致性（strict） |
| `pytest` | 单元与接口测试 |

> **提示**：当前仓库未附带 Alembic 版本目录。模型变更后，开发环境用 `init-db` 重建空库；已有环境的 DDL 需要人工编写并在预发验证。

## 十、代码风格

- 行宽 110，双引号，4 空格缩进（Ruff 统一）。
- 导入顺序：标准库 → 第三方 → 本项目，Ruff 自动整理。
- 私有函数以 `_` 开头；服务模块内聚，不跨模块调用私有函数。
- 异常信息面向最终用户，避免泄露表名、SQL、堆栈。
- 注释解释「为什么」，不复述代码。
