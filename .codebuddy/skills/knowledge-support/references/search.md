# 检索模式

给代码开发、方案设计、技术选型、论文理解、官方 API 使用、库更新、benchmark 规则提供可追溯的外部依据。

## 触发信号

- 用户明确要求联网、检索、查资料、查论文、查官方文档、查 GitHub、查 benchmark、查最新进展。
- 信息可能近期变化：模型版本、API、库用法、框架能力、许可证、价格、标准、论文结论、数据集规则、release notes、供应商政策。
- 代码生成、技术选型、架构设计、文档编写依赖外部事实。
- 另一个技能需要外部依据支撑结论。
- 用户问"现在主流怎么做""有没有官方实现""最新版本怎么用""这个库还推荐吗"。

## 来源优先级

1. 官方文档、标准、RFC、供应商文档、官方 release notes。
2. 作者仓库、官方 GitHub、论文代码、数据集主页、benchmark 官方页面。
3. 一手论文、会议页面、作者主页、arXiv、OpenReview、ACL Anthology。
4. 高质量技术博客、工程实践文章、项目 issue、维护者讨论、迁移指南。
5. 社区问答、论坛、社交媒体**只作补充，不能作为唯一依据**。

## 最小检索流程

1. **明确任务类型**：官方 API/库用法确认 / 代码生成前技术选型 / 论文与 benchmark 调研 / 工程方案对照 / 许可证与价格与兼容性核对。
2. **拆关键词**：用户原始中文问题 + 英文关键词、同义词、论文术语、库名、版本名、接口名。
3. **优先查一手来源**：
   - API / 库任务：至少查官方文档或官方 release notes。
   - 论文 / benchmark：至少查论文、会议页面、作者仓库或官方主页。
   - 工程选型：至少查官方文档、维护者仓库或权威迁移说明。
4. **来源分层**：哪些是已确认事实、哪些来源冲突、哪些是工程推断、哪些仍需真实环境验证。
5. **只把可靠来源写进结论**。只有二手来源时必须说明"证据不足"，不能写成确定事实。

## 输出结构

1. **问题重述**：这次检索要解决什么决策或事实。
2. **检索关键词**：中文 + 英文。
3. **核心发现**：按官方规范 / 论文依据 / 工程实践 / 社区补充分组。
4. **结论分层**：已确认事实 → 来源冲突与取舍 → 工程推断 → 仍需真实验证的边界。
5. **项目落地点**：对模块、流程、接口、数据、测试、文档的影响；如果只是背景知识，明确说明不直接落代码。
6. **来源清单**：可点击链接 + 来源类型 + 年份或更新时间。

## 服务于代码生成时的额外要求

必须把结论转成工程约束：

- 推荐用哪个官方 API、库、协议、格式或实现路径。
- 不推荐什么做法，原因是什么，依据来自哪里。
- 当前项目的最小可行实现是什么。
- 哪些只能作为后续扩展，不能包装成当前已完成能力。
- 需要新增或更新哪些测试、smoke test、文档或验证证据。
- 来源和当前项目环境不匹配时，说明差异和需要真实环境验证的边界。

## 质量要求

- 不允许只写"网上说""资料显示"。
- 不允许只给二手转述。
- 不允许把论文、博客或官方能力夸大成当前项目已实现。
- 涉及现代库、API、模型、标准、许可证、价格或 benchmark 时，必须核对最新官方来源。
- 来源冲突必须说明冲突点、取舍理由和仍需验证的部分。
- 网页无法访问时说明限制，改用可访问的一手来源。

## 竞品类检索的额外要求

- 用户真实抱怨（应用商店评论、GitHub issues、社区讨论）的价值高于功能列表——功能列表说"它有什么"，抱怨说"它哪里让人想走"。
- **查不到就写"未查到"，绝不允许凭印象补全竞品功能。** 用户一旦发现一条编造，其余结论全部作废。
- 标注信息日期。超过一年的一手来源要重新确认。
