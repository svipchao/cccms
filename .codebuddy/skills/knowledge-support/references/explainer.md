# 讲解模式

把技术原理、核心概念、公式含义讲清楚，目标是让用户**能听懂、能复述、能迁移到自己的项目**。

适用于：技术原理讲解、八股讲解、从零教学、面试口述、项目追问回答、领域补课。

## 最高约束：字数硬门槛

输出必须是**两层结构**，任一层不达标即判定输出失败，必须继续补写后再交付：

1. **可直接口述回答（快速复习总结）**：不少于 **1000 字**。
2. **详细原理讲解（通俗版，含公式）**：不少于 **3000 字**。

字数下限是最低门槛，不是目标上限。禁止刚超过 1000 / 3000 字就停笔。必须根据问题复杂度动态扩展，确保用户真的能听懂。

**禁止以提纲化压缩的方式交付。** 提纲不是讲解。

## 输出结构

### 第一部分：可直接口述回答（≥1000 字）

面向"被问到要能立刻说出来"的场景。要有清晰的结构骨架，让用户记住顺序，而不是背散点。

### 第二部分：详细原理讲解（≥3000 字，含公式）

必须**从最基础概念开始**递进，不要假设用户已经懂前置知识。

必须包含：

- **公式解释**：每个公式里每个符号是什么、量纲/取值、直观意义是什么。只写公式不解释符号等于没讲。
- **符号解释**：出现的下标、上标、运算符含义。
- **直观意义**：这个公式在物理/工程上到底在做什么。
- **案例**：至少一个具体例子走完全流程。
- **比喻**：用一个生活化类比帮助建立直觉。
- **记忆抓手**：给一个能勾住整个知识点的短句或结构。

### 第三部分：项目落地点

这个知识点在当前项目里落在哪：哪个模块、哪段代码、哪个设计取舍。如果只是背景知识，**明确说明不直接落代码**，不要硬凑。

### 第四部分：面试官 / 评审者追问

列出对方最可能追问的 3~5 个问题，并给出回答要点。

### 第五部分：未实现能力边界

必须区分四类，不允许混着说：

- 已经实现的
- 正在设计的
- 后续可扩展的
- 需要真实验证的

**把"论文里有""官方支持""博客说可以"说成"我们已经实现"，是最严重的错误。**

## 质量门槛

- 不允许用"简单来说就是这样"跳过难点。
- 不允许只给结论不给推导路径。
- 不允许出现无法复述的长句堆砌。
- 涉及最新论文、官方文档、benchmark、争议结论、现代 API 时，**必须先走检索模式**建立依据，再讲解。
- 比喻要准确。一个错误的比喻比没有比喻更糟，因为它会在用户脑子里留下错误模型。

## 自检

1. 第一部分不少于 1000 字？
2. 第二部分不少于 3000 字？
3. 从最基础概念开始了吗？
4. 每个公式的符号和直观意义都解释了吗？
5. 有具体案例走完全流程吗？
6. 有比喻和记忆抓手吗？
7. 项目落地点写了吗（或明确说明不落代码）？
8. 列了 3~5 个追问及回答要点吗？
9. 已实现 / 设计中 / 可扩展 / 待验证区分清楚了吗？
10. 涉及最新事实时先检索了吗？
