# knowledge-support

## 定位

两种模式，共同目标是**让后面的判断有依据**。

- **检索模式**：外部事实可能已经变化时，先建立可追溯依据。
- **讲解模式**：用户缺少背景知识时，先把原理讲清楚到能复述、能迁移。

两个模式经常连用：讲解涉及最新论文、官方文档、benchmark 或争议结论时，先检索再讲。

## 模式选择

| 用户说 | 进入 |
|---|---|
| 查一下、最新版本、官方怎么说、有没有官方实现、现在主流怎么做、这个库还推荐吗、benchmark 规则 | 检索模式（`references/search.md`） |
| 讲讲原理、从零教、面试问这个怎么答、这个概念到底是什么、这段公式什么意思 | 讲解模式（`references/explainer.md`） |
| 涉及前沿技术且用户明显不懂 | 先检索，再讲解 |

## 不触发

- 用户明确要求不联网、只基于本地材料回答。
- 本地源码、README、测试日志已经足够回答，且不依赖最新外部信息。
- 纯文件整理、格式修复、已有的本地调用链总结。

## 共同底线

1. **一手来源优先**。官方文档、官方仓库、release notes、论文、标准 > 二手转述。
2. **区分四类表达**：`已确认事实` / `来源冲突` / `工程推断` / `仍需真实验证`。禁止混着写。
3. **不接受不可追溯的表达**。"网上说""资料显示""一般来说"一律不算依据。
4. **不把外部能力夸大成项目已实现**。论文里有、博客里说、官方支持，都不等于当前项目做了。
5. **来源冲突时**说明冲突点、取舍理由、仍需验证的部分，不要挑一个听起来顺的。
6. **网页打不开就说清限制**，改用可访问的一手来源，不要用记忆补全。
7. 全程简体中文，专有名词、命令、代码保留英文。

## 输出结构

**检索**：问题重述 → 检索关键词 → 核心发现（按来源类型分组）→ 结论分层 → 项目落地点 → 来源清单（链接 + 类型 + 日期）。

**讲解**：概念定位 → 从最基础概念递进 → 公式与符号的直观意义 → 案例与比喻 → 项目落地点 → 面试追问 → 复述抓手。双层结构，见 `references/explainer.md` 的字数硬门槛。

## 自检

检索：满足触发条件且用户没要求不联网吗？至少用了一手来源吗？有可追溯链接吗？区分了事实/冲突/推断/未验证吗？服务于代码时转成工程约束了吗？

讲解：字数达标了吗？从基础概念开始了吗？公式有直观意义解释吗？区分了已实现/设计中/可扩展/需验证吗？涉及最新事实时先检索了吗？
