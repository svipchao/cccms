# 诊断模式

工作目录即项目根目录。**项目背景由你自己读出来，不要让用户填表。**

## 第 0 阶段：自我勘察

### 要查的八项

| 项 | 从哪读 |
|---|---|
| 项目形态 | 根目录结构 + 特征文件：`manifest.json` 是浏览器扩展；`package.json` + 前端目录是 Web 前端；`pyproject.toml`/`go.mod`/`Cargo.toml` 看语言；有 server/entry 是服务；有 bin/entry_points 是 CLI；多包目录是 monorepo |
| 项目是什么 | README 首段 / `package.json` 的 `description` / 仓库名 / `docs/` |
| 目标用户 | README 使用场景、截图、功能列表反推。禁止写"所有开发者"这类空话 |
| 技术栈 | 依赖文件 + 配置文件（tsconfig、vite.config、webpack.config、Dockerfile） |
| 当前版本 | `version` 字段、`manifest.json`、git tag、CHANGELOG 最新条目 |
| 构建与发布 | `scripts` 字段、`.github/workflows/`、`Makefile`、发布配置 |
| 已有约定 | `AGENTS.md`、`.codebuddy/`、`.editorconfig`、lint 配置、贡献指南。**这些是硬约束，后续必须遵守** |
| 数据与状态 | schema、migrations 目录、IndexedDB/localStorage 用法、数据文件 |

### 输出格式

先输出表，然后继续，不要停下等确认：

```
| 项 | 结论 | 来源（相对路径） | 置信度 |
|---|---|---|---|
| 项目形态 | 浏览器扩展（MV3） | manifest.json | 确认 |
| 目标用户 | 刷题备考的人 | README.md#L12 | 推断 |
```

置信度三档：`确认`（有明确文件依据）/ `推断`（依据存在但需间接推理，写清链条）/ `待确认`（找不到依据，标出来并按最合理假设继续）。

### 三条硬规则

1. **不许把推断写成确认**。技术栈、用户群必须有依赖文件或文档支撑，不能凭目录名猜。
2. **不许因为查不到就停下**。标 `待确认`，写出采用的默认假设，继续。**缺 README、缺文档、缺 CHANGELOG 本身就是 P1 级发现**，写进问题清单，不是障碍。
3. **只有一种情况允许问用户**：信息缺失会导致整个分析方向错误（如根本看不出项目形态），且用户一句话能回答。最多 1 个问题，**必须同时给出默认假设**，让用户只需回"是"或改一个字。

### 顺手自己决定的两件事

- **报告放哪**：优先已存在的 `docs/` 或 `reports/`，都没有就在项目根新建 `reports/`。说明"报告将写入 X，理由 Y"，不要问。
- **竞品从哪来**：从 README、description、功能列表推断领域与关键词，自己检索 3~5 个。无法联网时明确说明，并把竞品分析降级为"基于本地材料和通用认知的初步判断"，标注不可作为决策依据。

## 八维分析

每项都回答：**现状 → 证据 → 具体问题 → 影响谁、多严重**。

1. **功能完整性**：文档承诺但代码没有的空壳功能；代码有但文档没提的；半成品（入口走不通、只有主路径没有异常路径）；功能断裂（A 产出 B 没接上）。
2. **代码与架构**：**平行链路**（同一能力两套实现，改一处忘一处，重点查）；模块耦合度；三处以上重复逻辑；死代码、注释代码、永远为假的分支；命名与行为不符。
3. **数据与状态**：存哪、结构、有没有版本号、升级怎么迁移；备份/恢复/导出是否真可用；并发竞争；删除语义与孤儿数据。
4. **性能与体验**：明确瓶颈点；首次加载/冷启动；等待有没有反馈；出错时用户看到什么。
5. **安全与隐私**：权限是否最小必要、有没有申请未用；敏感数据存哪、会不会进日志；外部输入校验；第三方请求去向。
6. **可维护性与工程化**：测试有无与能否跑起来（能跑就贴真实输出）；构建发布能否一条命令跑通、产物有没有混入不该有的文件；版本号在几处维护；依赖是否过时/重复/过大。
7. **文档与实现一致性**：逐条核对文档承诺与代码真实行为。这类不一致比 bug 更伤信任，因为用户照文档操作会失败。
8. **可观测性**：出错能否定位、日志有无上下文；用户有无反馈通道、报错信息对人有没有用。

## 强制约束

1. 只读。不改代码、不装依赖、不执行 git 写操作、不跑有副作用的命令。
2. 跳过噪声目录：`node_modules`、`.git`、`dist`、`build`、`venv`、`__pycache__`、`.next`、`coverage`。
3. 先建项目地图再谈问题。地图没建完就提建议，说明在猜。
4. 不为填表去读大量无关文件，够用就停。
5. 读到 `.env`、密钥、凭证文件时不输出内容，只说明"存在且位置在 X"。

## 竞品调研

选 3~5 个，覆盖三类并说明选择理由：**直接同类** / **相邻替代**（含"手动做"这种朴素方案）/ **跨行业标杆**（不同行业但某环节做得极好）。

### 每个竞品查什么

| 项 | 要求 |
|---|---|
| 核心功能矩阵 | 逐项标"有 / 无 / 部分支持"并注明限制，不要写"功能丰富" |
| **用户真实抱怨** | 应用商店评论、GitHub issues、社区讨论里**反复出现**的问题。全表最有价值的一列 |
| 定价与模式 | 免费 / 订阅 / 买断，限制在哪 |
| 更新节奏 | 最近一次发布时间，还在维护吗 |
| 上手门槛 | 安装到用起来几步，有无劝退点 |

### 来源分级

- **一手（可作结论依据）**：官方文档、官网、官方仓库、release notes、应用商店页面、论文/标准。
- **二手（仅作线索）**：技术博客、测评、社区讨论、社交媒体。

每条结论标：来源类型 + 链接 + 日期。**查不到就写"未查到"，绝不允许凭印象补全竞品功能。**

### 三关筛选

看到竞品有某功能，不能直接建议"我们也加"：

1. **需求是否真实**：有证据表明**我们的**目标用户需要吗？竞品用户 ≠ 我们的用户。
2. **不做会怎样**：丢用户、丢口碑，还是根本无感？
3. **做的代价**：涉及哪些模块、会不会破坏现有结构、维护成本多高？

三关过不了 → "明确不做"。过了一二关但代价过高 → "观察"，写明盯什么信号。

### 常见错误

把竞品功能清单当需求清单；只查官网不查抱怨；用"业界普遍都做"当理由；忽略"用户手动做"这个替代方案；信息过时（超过一年的一手来源要重新确认）。
