# 输出模板

## 一、诊断报告

路径：`{目录}/项目体检与竞品分析-{YYYY-MM-DD}.md`，UTF-8，简体中文。

### 1. 项目快照

一段话说清：这是什么、给谁用、当前阶段、核心链路怎么走。附项目地图（模块 + 数据流，文字或 Mermaid）。要求没接触过项目的人 5 分钟能看懂。

### 2. 问题清单

按 `P0 / P1 / P2 / P3` 分级，同级按影响面排序。某级没问题写"未发现"，不要删节。

| 级别 | 判定 |
|---|---|
| P0 | 数据丢失、安全风险、核心功能不可用 |
| P1 | 明显影响体验，或存在回归风险 |
| P2 | 可维护性问题、局部不一致 |
| P3 | 打磨项 |

```markdown
### P1-3 · {一句话问题}

- **级别**：P1
- **位置**：[文件](相对路径#L行号)
- **现象**：实际发生了什么
- **证据**：文件片段 / 命令输出 / 链接
- **影响**：影响谁、什么场景下会出事
- **建议**：可行方向 + 涉及文件 + 预期收益
- **验证方式**：怎么证明改完真的好了
```

字段缺失即不合格，不允许只写"建议优化"。

### 3. 竞品对比矩阵

```markdown
| 维度 | 本项目 | 竞品A | 竞品B | 竞品C |
|---|---|---|---|---|
| 核心功能X | 有 | 部分支持（限制：…） | 无 | 有 |
| 上手门槛 | 3 步 | 5 步 | 2 步 | — |
```

表后补一段：**我们相对竞品的真实优势**。禁止写"我们更轻量""我们更专注"这种谁都能说的话。

### 4. 功能缺口池

三档：**建议做**（理由 + 涉及模块 + 优先级）／**观察**（现在不做，盯什么信号）／**明确不做**（为什么不值得）。每个功能写清三关结论。

### 5. 优化改进清单

按**投入产出比**排序，不按严重程度。每条：改哪里、解决什么问题、预期收益、风险、验证方式。分「低成本高收益（先做）」和「高成本高收益（规划）」。

### 6. 明确不做什么

与"要做什么"同等重要。列不建议做的方向及原因，包括看起来该做但实际不划算的。用于防止后续反复讨论同一件事。

### 7. 需要拍板的决策点

2~4 个真正需要用户选择的问题。每个说明：为什么必须决定、不同选择的后果、倾向哪个及理由。**不要替用户拍板**，也不要把琐碎实现细节包装成决策点。

### 8. 附录

证据索引 / 检索来源清单（链接 + 类型 + 日期）/ 未覆盖范围及原因 / **待确认项**（第 0 阶段所有 `待确认` 项及其可能影响的结论）。

## 二、修改记录

路径：`{报告目录}/修复记录-{YYYY-MM-DD}.md`，追加写入，不覆盖历史批次。

### 工单表（开始时写一次，后续只更新状态）

```markdown
| ID | 来源 | 级别 | 类型 | 改动文件 | 风险 | 验证方式 | 批次 | 状态 |
|----|------|------|------|----------|------|----------|------|------|
| A1 | 报告 P2-3 | P2 | 修复 | popup.ts | 低 | 手动打开面板 | 1 | 完成 |
| B1 | 功能缺口池 | — | 完善 | — | 高 | — | — | 待确认 |
```

状态只有：`待做` / `进行中` / `完成` / `卡住` / `跳过`。

### 每批记录

```markdown
## 批次 1 · {YYYY-MM-DD HH:mm}

### A1 · {问题一句话}

- **位置**：[popup.ts](src/popup/popup.ts#L42)
- **改了什么**：{具体改动。不要写"优化了逻辑"，要写"在 X 为空时提前返回并用空态渲染替代 null 断言"}
- **为什么这么改**：{依据报告哪条 + 真实调用链结论}
- **验证**：`{命令}` → {真实输出摘要}；或手动步骤：{步骤} → {观察到什么}
- **未验证的部分**：{写清楚哪些路径没跑到；没有就写"无"}
- **风险与遗留**：{改完可能影响什么；没有就写"无"}
- **回滚方式**：{改回哪几行 / 撤销哪个提交 / 恢复哪个文件}
```

### 批次小结

```markdown
### 批次 1 小结

- 完成：A1、A2
- 跳过：{ID} —— {原因}
- 连带影响：{有没有波及其他模块}
- 下一步：进入批次 2（A3、A4）
```

### 填写要求

1. "改了什么"必须具体到行为。**"优化了逻辑""提升了健壮性""增强了容错"一律不写，写了等于没写。**
2. "验证"必须是真实执行过的命令和真实输出。没跑就写"未验证"，不要编造输出。
3. "回滚方式"是硬性字段。填不出来说明改动范围不清，应该回头缩小改动。
4. "未验证的部分"宁可多写。诚实标注边界比假装全覆盖有价值。
5. 卡住的工单要记录卡在哪、缺什么信息、需要用户做什么决定。

### 收尾总结

```markdown
## 本轮总结

- 修复：{N} 条（P0 {n} / P1 {n} / P2 {n} / P3 {n}）
- 跳过：{N} 条，原因：{一句话汇总}
- 验证覆盖：{N} 条有命令验证 / {N} 条仅手动 / {N} 条未验证
- 待用户决定：{轨道 B 条目数}
- 未执行：{轨道 C 条目数}
- 新发现（未修复）：{列表}
```
