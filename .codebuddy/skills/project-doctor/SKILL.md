# project-doctor

## 定位

一个技能，两个模式，一条链路：**先诊断，再施工**。

- **诊断模式**：只读。产物是报告，不改一行代码。
- **施工模式**：按报告改代码。产物是代码改动 + 修改记录。

**为什么必须手动触发**：诊断要读大量文件并联网查竞品，成本高，不该被一句"这项目是干嘛的"误触发；施工会改代码，更不该自动执行。所以整体设为 `/project-doctor` 手动发起。

## 模式切换规则

| 用户说 | 进入 |
|---|---|
| 分析、体检、查漏补缺、看缺什么功能、对比竞品、优化空间 | 诊断模式 |
| 按报告修复、自动修复、把这些改掉、修 P0、落实改进 | 施工模式 |
| 没说要改什么，只是问"有什么问题" | 诊断模式 |

**施工模式的前置条件**：必须存在体检报告。找不到就切回诊断模式或提示用户先诊断，**不允许凭印象改代码**。

跨模式时读现有报告，不要重新体检一遍。

## 共同底线

1. **报告不等于真相**。施工前每条都要复核；误报、已修复、判断过重的直接剔除并说明。照着误报修，就是制造新 bug。
2. **修复优先于新增**。先填坑再谈加功能。带着 P0 去开发新功能是最差的选择。
3. **结论必须有证据**。只认三种：文件路径 + 行号、命令真实输出、可点击外部链接。
4. **不许把推断写成事实**。每条结论标 `已确认事实` / `来源冲突` / `工程推断` / `待验证`。
5. **改完必须能证明改了**。没跑过命令就不能写"已验证"。
6. **只读阶段不写文件**。诊断模式除报告外不改任何文件、不装依赖、不执行 git 写操作。

## 输出约定

- 全程简体中文。代码、命令、路径、报错原文、专有名词保留英文。
- 路径用相对项目根的相对路径；指向代码用 `[文件名](相对路径#L行号)`，不要把 `:42` 塞进链接目标。
- 涉及外部信息标注检索日期和来源更新时间。
- 同一概念全文一种叫法；项目术语与通用叫法不一致时首次出现说明对应关系。
- 准确优先。20 条真问题胜过 100 条"建议优化"。

## 诊断模式

详见 `references/audit-mode.md`。核心是三步：

1. **第 0 阶段自我勘察**：自己从特征文件读出项目形态、定位、技术栈、版本、构建方式、已有约定、数据状态，输出带来源和置信度（确认/推断/待确认）的推断表。**不让用户填表**，也不因查不到就停下。
2. **八维分析**：功能完整性、代码与架构、数据与状态、性能与体验、安全与隐私、可维护性、文档一致、可观测性。每项都要"现状 → 证据 → 问题 → 影响"。
3. **竞品调研**：3~5 个，覆盖直接同类、相邻替代、跨行业标杆。铁律是**从"竞品有"到"我们该做"必须过三关**（需求真实 / 不做的后果 / 做的代价）。

报告结构见 `references/templates.md`。

## 施工模式

详见 `references/fix-mode.md`。核心是四步：

1. **复核**：把报告条目分成真实存在 / 已修复 / 误报 / 级别有误 / 无法复现，先出复核结果表。
2. **三轨道分诊**：A 修复（自动做）／ B 完善功能（每项先确认）／ C 重构改进（默认不做，只出方案）。**功能加错比 bug 难回滚**。
3. **排工单**：一批最多 3 单、5 个文件。P0 单独一批。
4. **逐批施工**：读真实调用链 → 锁定边界 → 改 → 真跑命令验证 → 写记录。一批一汇报。

修改记录模板见 `references/templates.md`。

## 红线（施工时碰到必须停）

1. 影响对外接口、数据格式、存储结构、权限声明。
2. 需要引入新依赖或升级依赖。
3. 需要写数据迁移。
4. 改动超过 5 个文件，或需重命名/移动核心模块。
5. 报告里两条建议互相冲突。
6. 根因不在报告指出的位置。
7. 测试/构建环境跑不起来，无法验证。
8. 修复需要删除现有功能或用户数据。

停下时说清：哪条工单、卡在哪、倾向怎么处理、不处理会怎样。**给选项让用户选，不要只抛问题。**

## 负面清单

1. 不只读阶段写文件，不擅自跑破坏性命令。
2. 不凭记忆断言竞品功能、库版本、平台规则；查不到写"未查到"。**编造竞品功能是最致命的错误。**
3. 不把"业界最佳实践"当成本项目的问题——通用规范要落到具体位置才算数。
4. 不为显得全面而堆砌低价值问题。
5. 不建议没有依据的防御性代码（固定超时、长度截断、条数上限、静默降级、空 catch）。
6. 不建议大范围重构作为默认方案；要提就说明根因、必要性、影响范围、回归方案、可回滚边界。
7. **不吞异常**。禁止空 `catch`、`try/except: pass`、把错误静默降级成默认值。
8. **不为让测试通过而改测试**。
9. 不改没有工单覆盖的文件；看到别处问题只记进"新发现"。
10. 不写"优化了代码结构""提升了健壮性""建议进一步优化"这类无法核查的表述。
11. 不修改体检报告本身来让自己施工看起来合理。
12. 不输出密钥、token、个人数据实际内容。
13. 不在轨道 B/C 上擅自动手。

## 自检

**诊断后**：推断表标了来源和置信度吗？每条问题有可跳转位置吗？每条建议写了"改哪里、收益、风险、怎么验证"吗？"明确不做什么"写了吗？竞品结论有来源和日期吗？决策点 2~4 个吗？有没有换成任何项目都成立的废话？

**施工后**：复核结果表出了吗？有没有改到工单之外的文件？每条修复有真实命令输出吗？修改记录的"验证"和"回滚方式"填了吗？版本号同步了吗？碰到红线停了吗？

## 收尾

**诊断**：给报告路径、最该先处理的 3 件事、需要拍板的决策点、推断表里值得确认的项。用户要继续，提示执行 `/project-doctor 修复`。

**施工**：给修复统计、验证总览（哪些跑过测试 / 仅手动 / 未验证）、轨道 B 方案清单、轨道 C 建议（标注"本轮未执行"）、新发现、下一步建议。
