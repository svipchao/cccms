# prompt-writer

## 定位

这个技能**不执行任务**，它生产"给 AI 用的文字资产"。调用它，产物是一段可复制的 prompt 或一份规则文件，不是代码改动。

**最容易误解的地方**：用户说"帮我审一下代码"时，如果只是要结论，直接审查即可，不必走本技能；只有用户想要一份**可复用的审查指令**时才用 review 模式。

## 五种模式

| 模式 | 触发 | 产物 | 详细规则 |
|---|---|---|---|
| `agents-md` | 写/更新 AGENTS.md、整理项目规则 | 项目根 `AGENTS.md` | `references/agents-md.md` |
| `task-prompt` | 把需求写成 prompt、开发/修复/验证/交接任务 | 一个 Markdown 文本块 | `references/prompts.md` |
| `plan-prompt` | 先计划、先给决策点、别急着改代码 | 要求进入 Plan mode 的 prompt | `references/prompts.md` |
| `review-prompt` | 审查 diff / PR / 指定文件 / 发布前风险 | 审查 prompt（找问题，不直接修） | `references/prompts.md` |
| `new-skill` | 把这个流程沉淀成 skill、做成项目工具 | 新 skill 目录 | `references/new-skill.md` |

选择规则：

- 规则要**长期生效** → `agents-md`
- 只是**这一次**要做的事 → `task-prompt`
- 方向没定、怕返工、需要用户拍板 → `plan-prompt`
- 要检查已有改动有没有问题 → `review-prompt`
- 同一套流程**反复出现且输入输出稳定** → `new-skill`

## 共同底线

1. **先读目标项目的真实材料再动笔**：`AGENTS.md`（若有）、README、开发日志、测试说明、与任务相关的真实调用链。不许凭想象填充。
2. **项目事实只能来自项目**。路径、命令、版本号、发布方式必须能在仓库里指到出处。无法确认的写成 `{{待确认}}` 或明确标"待确认"。
3. **不复制别的项目的私有信息**。旧项目的模块名、测试命令、审核规则、版本号都不是通用规则。
4. **不写空话**。每条约束都要可检查、可执行、可交付。"注意代码质量"不是约束。
5. **不把未验证写成已验证**，不把推测写成事实。
6. 全程简体中文。代码、命令、路径、报错原文保留英文。

## 让 prompt 真正可执行的四个习惯

1. **负面清单比正面要求更有用**。"不要吞异常""不要为过测试改测试""不加没有依据的防御性代码"这类禁止项，能挡住大部分跑偏。
2. **要求执行者给证据**。每条结论要能落到文件行号、命令输出或链接上。
3. **要求分层表达**。区分 `已确认事实` / `来源冲突` / `工程推断` / `待验证`，避免把猜测当结论。
4. **给出停止条件**。什么情况下必须停下来问人，比"尽量做好"有用得多。

## 引用其他技能

生成的 prompt 里如果需要指向另一个技能，统一用 `/skill-name` 形式（如 `/project-doctor`），不要只写反引号包裹的名字，也不要写成普通文件名。

## 输出包裹

`task-prompt` / `plan-prompt` / `review-prompt` 三种模式的最终产物必须**整体放入一个 Markdown 文本块**，方便用户一键复制。若 prompt 内部含三反引号，外层用四反引号或更长围栏。输出代码块前后不要加额外正文。

## 自检

1. 是否先读了项目真实材料？
2. 项目事实是否都有出处？没有的是否标了待确认？
3. 有没有残留别的项目的私有路径、模块名、命令、规则？
4. 长期规则有没有误塞进一次性 prompt，或反过来？
5. 约束是否可检查、可执行？有没有"注意质量"这类空话？
6. 负面清单写了吗？
7. 需要拍板的地方有没有替用户决定？
8. 三反引号包裹、可一键复制做到了吗？
9. 交叉引用是否统一用 `/skill-name`？
