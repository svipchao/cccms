# new-skill 模式

把反复出现的流程沉淀成项目本地 skill。

## 什么时候该建

- 某类任务反复出现，每次都需要相似的读取顺序、边界判断和输出格式。
- 有清晰触发词、适用场景和**不适用**场景。
- 需要引用专属模板、检查清单、示例输出或脚本。
- 与项目规则相关，但比 `AGENTS.md` 更具体、更偏流程。
- 用户明确希望把流程变成后续可调用的工具。

## 什么时候不该建

- 只有一次性需求 → 用 `task-prompt`。
- 需求还没稳定，输入输出边界都在变 → 先跑几遍再说。
- 只是几条长期规则 → 写进 `AGENTS.md`。
- 只是先计划后执行 → 用 `plan-prompt`。
- 只是 code review → 用 `review-prompt`。
- 想把所有规范塞进一个万能 skill → 职责混乱，必然失效。

## 目录与文件

```
.codebuddy/skills/<skill-name>/
├── SKILL.md          必须有
├── references/       需要专属模板、较长清单或示例输出时才建
├── scripts/          需要可复用自动化脚本时才建
└── assets/           需要图片、示例数据等静态资源时才建
```

**不创建空目录、空模板、"以后可能用得上"的占位文件。**

## SKILL.md 要求

frontmatter：

```yaml
---
name: <与目录名完全一致，小写字母+数字+连字符>
description: <做什么 + 什么时候用。触发词写全，这是模型决定是否调用的唯一依据>
# disable-model-invocation: true   # 会写文件或改代码的技能必须加
---
```

- `name` 必须和目录名一致，否则加载失败。
- `description` 里要写清**触发场景的具体说法**，不是功能简介。
- **会写文件、改代码、执行有副作用操作的技能，必须加 `disable-model-invocation: true`**，只允许手动 `/skill-name` 触发。模型不该因为用户随口一提就自动开始改东西。

body 必须包含：技能定位、触发与不触发、使用流程、硬约束、输出要求、自检项。

## 写作要求

- 只写必要文件。`SKILL.md` 讲判断逻辑和约束，长模板挪进 `references/` 按需加载。
- 必须写明：什么时候读 `references/`、什么时候跑 `scripts/`。
- 交叉引用其他技能统一用 `/skill-name`。
- 命名用小写字母、数字、连字符；表达"动作 + 对象"，如 `project-doctor`；不要用 `skill-creator`、`helper` 这类容易和系统技能撞名的名字。
- 不复制别的项目的私有路径、模块名、版本号、测试命令、发布规则。

## 验证

创建后至少检查：

- frontmatter 可解析，`name` 与目录名一致，`description` 存在且包含触发词。
- 被引用的 `references/`、`scripts/` 文件真实存在。
- 中文 Markdown / YAML 为 UTF-8 可读。
- 没有英文占位说明、空标题、私有硬编码、一次性任务残留。

## 自检

这个流程真的值得沉淀吗（还是用一次就够）？职责单一吗？触发清楚吗？有没有把多个无关行为堆进一个技能？有没有撞名？是否只建了必要文件？
