# agents-md 模式

生成或更新项目级 `AGENTS.md`。它回答：Agent 开始工作前必须知道什么、什么不能做、怎么验证、怎么汇报、什么时候升版或写报告。

**它不是一次性任务 prompt，也不是别的项目规则的复制品。**

## 使用流程

1. 确认项目路径、项目类型、主要系统与 shell、用户希望长期生效的规则范围。
2. 读取最小真实上下文：已有 `AGENTS.md`、README、开发日志、贡献指南、测试说明、发布说明、入口文件、配置文件、脚本清单、包管理文件。
3. 按目标项目事实裁剪模板，用真实值替换占位符。不适用的专项段落直接删除，不要留空标题。
4. 区分三类内容：
   - **长期底线**：不把未验证写成已验证、不吞异常、不做无关重构、先读真实调用链。
   - **项目事实**：真实目录、真实命令、真实版本策略、真实发布方式。
   - **可选偏好**：只有用户确认或项目证据支持时才写入。
5. 旧规则与目标项目事实冲突时，以目标项目当前文件和用户最新决策为准。

## 必须包含的段落

缺任何一段都不合格：

1. **执行环境前置规则**：操作系统、shell、命令语法差异、编码要求（UTF-8）。
2. **顶层代码生成约束**：语言风格、禁止事项、错误处理边界。
3. **修改前必读**：哪些文件必须先看（README、开发日志、相关模块）。
4. **真实仓库结构**：真实目录职责，不许写想象的结构。
5. **真实调用链要求**：改之前先理解谁调用了它。
6. **版本规则**：版本号维护在哪些文件、什么时候升位。
7. **修改记录要求**：改完要写什么（范围、验证方式、证据路径、未验证边界、风险）。
8. **测试验证**：真实可执行的测试命令，不许写"运行测试"这种空话。
9. **输出与验收格式**：交付时怎么说明改了什么、怎么验证、还有什么没覆盖。
10. **进度播报格式**：长任务时必须输出可观察的进度块。
11. **错误处理**：显式暴露问题，禁止吞异常和伪造成功。
12. **无依据保护逻辑的判断框架**：新增超时、截断、重试、降级、默认值前，必须说明依据、影响、可观测性、验证方式。

## 报告链接规则（原文保留，不得改写）

> 生成报告时必须使用可跳转的 Markdown 相对路径交叉引用。链接优先落到具体文件名，能定位到行号时必须使用 `[文件名](相对路径#L行号)` 范式；不要把 `:行号` 写进链接目标里。不要只写文件夹名代替关键证据，也不要使用当前 IDE 无法跳转的绝对路径，必须强制使用相对路径。

## 进度播报格式

```
> 🧩 步骤：{一句话描述正在做什么}
> 🎯 目的：{为什么要做}
> ▶️ 执行：{命令、页面、文件路径或操作}
> ✅ 结果：{当前状态}
> 🧾 证据：{可验证证据路径}
> 📝 备注：{可选，最多一句}
```

## 最小化修改的边界

必须写清楚默认做**最小必要改动**，但也要说明**最小化不是盲目保守**。

如果只写"最小化修改"，Agent 会把它理解成只改几行，最后做出不符合真实用户需求、工业场景或业务实践的方案。更常见的问题是：两个平行功能 A 和 B 本应保持一致，Agent 只在 A 里补了新设计，B 里继续保留旧链路，后续维护越来越割裂。

所以要明确边界：面向真实用户需求、修反复多次未修好的 bug、或为贴合真实工业场景时，**允许更大范围重构**，但必须先说明根因、必要性、影响范围、回归方案和可回滚边界。

## 质量标准

- 最终文件要像项目规则，不像教程或建议书。
- 每条关键约束都可检查、可执行、可交付。
- 不写死旧项目的路径、模块名、测试命令、版本号、审核规则。
- 无法确认的事实写成待确认项，不要包装成规则。

## 落地建议（写给用户）

`AGENTS.md` 不需要一次写到完美。更好的做法是：先挑一个低风险小任务试跑，之后每次 Agent 犯了具体错误就往里补一条约束——"这个文件不能这么改""跑测试必须带这个命令"。让规则从真实踩坑里长出来，而不是凭空加原则。
