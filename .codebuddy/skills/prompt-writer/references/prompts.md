# 三种 prompt 的生成规则

三个模式的共同产物形态：**一段完整、连续、可一键复制的中文 prompt**，整体放入一个 Markdown 文本块。

## 通用流程

1. 先确认用户要的是"生成 prompt"，不是"直接执行任务"。
2. 读目标项目 `AGENTS.md`（若有）、相关 README、开发日志、测试说明、真实调用链。
3. 从用户输入和项目材料里提取：仓库路径、项目类型、当前版本、本轮目标、硬性边界、必读文件、必做事项、验证命令、交付物。
4. 按模式生成，删掉不适用的章节，不留空标题。
5. 输出前逐项自检（见各模式末尾）。

## 共同禁止项

- 不把未验证的事实写成已验证。
- 不新增没有依据的保护逻辑（固定超时、长度截断、条数上限、重试上限、静默降级、隐藏兜底）。这些不是"默认稳健"，只有存在用户要求、平台限制、项目既有约定或真实故障证据时才允许写。
- 不复制别的项目的模块名、测试命令、版本号、专项风险规则。
- 不保留空标题、空占位符、"视情况处理"这类不可检查的表达。

# 模式一：task-prompt

生成一次性任务的执行指令。产物是给执行 Agent 的 prompt，不是自己开始执行。

## 固定结构（不适用就删，不留空节）

1. **任务开场**：仓库、目标、"不允许跳过"的执行口吻。
2. `【硬性前置要求（必须先做）】`
3. `【项目定位与边界】`
4. `【版本与文档策略（必须遵守）】`
5. `【本次要完成的 TODO，必须全部落地】`
6. `【实现约束】`
7. `【测试与验证要求，必须执行】`
8. `【交付物要求】`
9. `【注意】`

## 补充规则

- TODO 多时按 `A / B / C / D` 分块；单任务只保留一个任务块。
- 保留用户原话中的硬性边界，再做项目化归纳。
- 涉及真实服务、用户数据、权限、外部系统、人工步骤或生产环境时，必须要求执行者写清验证边界和不可验证项。
- 不触发版本或报告时，要求执行者在最终总结里说明原因。
- 如果执行依赖外部最新知识（官方 API、库版本、论文、benchmark、标准、许可证），要求执行者先检索再下结论，不许把未检索的外部事实写成已确认。
- 需要指向别的技能时用 `/skill-name`。

## 自检

是否只是生成 prompt 而非执行？是否读了 AGENTS.md？有没有把 Plan mode 或 review 的规则混进来？交叉引用是否用 `/skill-name`？有没有无依据的保护逻辑？是否只有一个 Markdown 文本块？

# 模式二：plan-prompt

生成要求执行者先进入 Plan mode 的 prompt。**不直接给实现方案，不替用户做技术拍板。**

## 适用

高风险、多阶段、架构取向未定、用户明确要求"先计划""先给选择空间""先不要改代码"。

## 核心规则（prompt 必须要求执行者）

- 先使用 Plan mode。
- 不允许跳过计划阶段直接实现。
- 不允许一开始就写死详细技术方案。
- 不允许直接给用户几个已经具体到实现细节的方案让用户盲选。
- 先读真实仓库、参考材料和约束。
- 再提炼**少数真正需要用户拍板的决策点，控制在 2~4 个**。
- 决策点必须是大方向、结构取向、长期偏好或风险承受边界，不是琐碎实现细节。
- 每个决策点说明：为什么必须决策、不同取向影响什么、当前倾向是什么——**但不替用户拍板**。
- 用户选择后再收敛具体方案，然后才进入实现。

## 质量要求

- 像执行指令，不像在解释 Plan mode 是什么。
- 不要把用户能通过读仓库自己解决的问题扔给用户。
- 决策点超过 4 个，通常说明还没完成归纳。

## 自检

是否明确这是生成 Plan mode prompt 而非直接执行？是否要求先只读探索？决策点 2~4 个？有没有替用户拍板？

# 模式三：review-prompt

生成 code review prompt。**默认只出审查报告，不直接改代码。**

## 适用

审查当前分支 diff、指定 commit、PR diff、指定文件或目录；目标是发布前风险、行为回归、接口契约、文档一致性、安全隐私、测试缺口。

## 不适用

用户明确要求"直接 review 当前改动"并且只要结论 → 直接审查，不走本模式。

## 核心规则

**不要提供固定风险清单让执行者照单审查。** 固定清单会锁死范围，漏掉本项目真正重要的风险。

prompt 必须要求执行者先建立本轮**项目化风险地图**，至少回答：

- 本次改动可能改变了哪些对用户、调用方、维护者或发布流程的承诺。
- 哪些项目不变量、数据状态、交互边界、运行假设或文档承诺可能被破坏。
- 哪些失败模式最难被发现、最难恢复、影响面最大。
- 哪些证据足以证明本轮改动没有破坏关键路径。
- 哪些风险来自项目类型、审查范围、高风险领域、发布约束或用户明确边界。

可以给"风险维度示例"，但必须声明**它们只是启发，不是完整清单**，并要求执行者按真实仓库补充项目专属风险。

## 输出要求

- **findings first**，按严重程度排序。
- 默认只出审查报告和建议，不改代码。若用户要求"审查并修复"，也要求先出 findings，再由用户决定是否进入修复。
- 每条 finding 包含：严重级别、可跳转位置、证据、影响、可能的解决方案、验证建议。
- 每条问题都要给可行方向、涉及文件、预期影响和需要补充的验证。证据不足时不要强行拍板，可给 1~3 个方向。
- 审查报告单独保存为 Markdown；路径由用户指定或按项目习惯选（如 `docs/`、`reports/`），执行前说明路径。
- 报告至少包含：问题清单、严重程度、位置、证据摘要、影响、解决方案、建议验证、是否阻塞合并/发布、未覆盖风险与测试缺口。
- **没发现问题也要出报告**，说明未发现阻塞项、已检查范围、剩余风险和测试缺口。

## 自检

是否明确生成的是 review prompt 而非直接 review？范围与对比基准写清了吗？有没有改成固定清单？findings first 和证据链接要求有吗？无问题时也要出报告的规则有吗？
